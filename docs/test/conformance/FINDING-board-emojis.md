## 七、追加观察（纯本地几何分析，零设备风险）：总数可从几何推出

审核记录 21 说：想把 `ORIGINAL_TOTAL_EMOJI_COUNT` 冻结，需要"能证明 `rvEmojiList`
不可横向滚动、或数据集确实只有 6 项"的证据。**这份证据其实已经在 dump 里**，
不需要再做手势实验（而且**手势实验本身有风险**：emoji 行紧邻「留言」按钮，
误触即构成写操作 → 违反用户的只读硬约束，所以我不做）。

### 从 `message-board-dump.xml` 复算（任何人可重做）

```
rvEmojiList 容器:  x = [0, 1080]   宽 = 1080（= 整屏宽）
fl_emoji_root ×6:  宽均为 70
  左边界: 21, 133, 245, 357, 469, 581
  相邻左边界之差: 112, 112, 112, 112, 112   ← 间距恒为 112
最后一项右边界: 581 + 70 = 651
右侧剩余空间: 1080 - 651 = 429
```

### 推论

若存在第 7 项，按恒定 112 间距它会排在 **x = 693**，
其右边界 763 < 1080 —— **完全放得下、必然被布局并附着**，因此必然出现在 dump 里。
它没有出现，且右侧还空着 429px（不是"填满后截断"）。

→ **数据集就是 6 项**（前提假设：该行按固定 112 间距左起排布、不做分页/分组；
dump 中未观察到分组或分页迹象）。

### 因此可更新结论

```
ORIGINAL_TOTAL_EMOJI_COUNT: 6   ← 由几何推出（原为 NOT_EVALUATED）
EMOJI_SPACING:              112px  ← 由 dump 实测确认（原为 NOT_EVALUATED）
```

**但要如实标注强度**：这是**几何推论**，不是"把全部项都 dump 出来了"；
假设已写在上文。若审核要求更强的证据（例如证明该 RecyclerView 的 layoutManager
是横向且 itemCount 固定），需要能读取该控件内部状态的手段，目前没有。

### 一个值得记的细节：**一条旧记录可以"一半对一半错"**

旧记录 `supplements/message-board.json` 同时说了两件事：
- "恰好 **7** 个" → **错**（实际 6）
- "间距 **112px**" → **对**（与本次实测完全一致）

所以处理旧记录时**不能整条接受、也不能整条丢弃** ——

这比"整体信任/整体不信任"更符合这门纪律的本意。

## 八、审核记录 22 的术语纠正（重要，必须按此冻结）

审核**接受**了几何推论，但指出我把**术语**写得不精确 —— 而术语不精确会导致下游做错。

### 纠正 1：112px 是 **pitch（步距）**，不是 **gap（间隙）**

我实际直接测到的是：**相邻 item 左边界之差 = 112px**。
那是 **item pitch / stride**；因为每个 item 宽 70px，真正的 edge-to-edge gap 是：

```
112 - 70 = 42px
```

审核原话：**"不要笼统写 EMOJI_SPACING: 112px，否则以后有人按 CSS gap: 112px 复刻，会直接做错。"**

**因此按此冻结（替换我原先那句 `EMOJI_SPACING: 112px`）：**

```
EMOJI_ITEM_WIDTH:       70px    DIRECT_FROM_DUMP
EMOJI_ITEM_PITCH:      112px    DIRECT_FROM_DUMP
EMOJI_INTER_ITEM_GAP:   42px    DERIVED (112 - 70)
```

**旧 supplement 的处置**：它写的"间距 112px"如果本意是"相邻左边界距离"，那属于
**"数值正确、但字段语义不够精确"** —— 这与本 finding 早先的结论（该记录"一半对一半错"）
合并后的完整表述是：**数量错、数值对、命名不精确**。

### 纠正 2：总数结论的强度标注方式

```
ORIGINAL_TOTAL_EMOJI_COUNT: 6
EVIDENCE_TYPE:              GEOMETRIC_INFERENCE
CONFIDENCE:                 SUPPORTED
```

前提**必须继续保留在文档里**（因为它使结论可审计，而不是把推论伪装成直接观测）：
相同的布局规则、无分页 / 无分组 / 无特殊隐藏项。

审核对推理链的确认：容器完整覆盖 x=[0,1080]；6 个已附着 item 宽度一致；
left-edge pitch 恒为 112；若存在遵循同一布局规则的第 7 项，应位于 x=693..763，
**该区间完全处于当前 viewport 内**，所以不存在"因为超出屏幕所以没被 dump"的解释；
而实际不存在第 7 个 `fl_emoji_root`。

### 纠正 3：`EMOJI_CHARACTERS: NOT_CAPTURED` 保持不变（审核确认）

> 这部分不能因为"数量和几何已经恢复"就**反推出**字符内容。

### 本轮为什么值得单独记

我原先那句 `EMOJI_SPACING: 112px` **在数值上没错**，但它**把一个 stride 叫成了 spacing**。
这种错误不会当场暴露 —— 它会在**将来某人照着实现**时才变成 bug
（CSS `gap: 112px` vs 正确的 `width:70px + gap:42px`）。
**这与本项目"证据要可复算、命名要精确"的纪律是同一条**：
测量结果必须连同**它的定义**一起记录，否则"数字对了"照样会导出错误实现。

## 九、换算到我们的实现（implementation impact 的落地）

几何值原本是**原版设备像素**，要落到我们的 WebView 必须先确定换算基准：

```
设备密度: 280 dpi（adb shell wm density，只读）
→ dpr = 280 / 160 = 1.75
→ WebView CSS 视口宽 = 1080 / 1.75 ≈ 617（我们早前实测 618，吻合）
WebView 里 1 CSS px ≈ 1dp，故 设备px ÷ 1.75 = CSS px
```

| 量 | 原版（设备 px） | ÷1.75 | 我们的 CSS px |
|---|---|---|---|
| item 宽 | 70 | | **40** |
| pitch | 112 | | **64** |
| edge-to-edge gap | 42 | | **24** |

### 修正前的偏差（实测对比）

| 项 | 原版（CSS px） | 我们（修正前） | 差 |
|---|---|---|---|
| item 宽 | 40 | 34 | −6 |
| gap | 24 | **8** | **−16** |
| pitch | 64 | 42 | −22 |

即我们的表情行**明显更紧凑**。另外原版 6 项在整屏下右边界只到 651 设备 px、
**右侧剩 429px、根本不需要滚动**，而我们用了 `overflow-x: auto`
（现保留作防御，正常不应出现滚动条）。

### 已实施的改动

`app/src/screens/board.css`：`gap: 8px → 24px`、`width/height: 34px → 40px`，
并把**换算基准与术语警告**写进 CSS 注释（避免后人只看到数字、不知道它们是怎么来的）。

### 说明强度边界（不夸大）

- 这三个数是**从可复核 dump 换算得来**，但换算本身引入了两个假设：
  ①密度 280 → dpr 1.75（有 adb 读数支持）；②WebView 中 1 CSS px ≈ 1dp。
- 因此这是**依据证据的最优近似**，不等于"渲染结果与原版逐像素一致"。
  **不声称 pixel-level 1:1** —— 圆角、字号、底色等仍未比对。

## 十五、C5（新发现）：原版表情项**没有底色**，我们画了灰色圆片

### raw_evidence

`docs/test/original-baseline/raw-dumps/emoji-row-crop.png`（按 dump 坐标精确裁切，缩放系数=1 已验证）

### observation（像素采样，可复算）

首项 bounding box（设备 px）x=[21,91] y=[1711,1781] → 裁切坐标 x=[21,91] y=[11,81]；
圆心 ≈ (56,46)、半径 ≈ 35。采样结果：

```
顶中 (56,13) 距圆心33   → RGB(255,255,255)   ← 圆内
底中 (56,79) 距圆心33   → RGB(255,255,255)   ← 圆内
左中 (23,46) 距圆心33   → RGB(255,255,255)   ← 圆内
右中 (89,46) 距圆心33   → RGB(255,255,255)   ← 圆内
圆形外的角 (24,14)      → RGB(255,255,255)
字形中心 (56,46)        → RGB(255,222,49)    ← 黄色字形
项外空白 (112,46)       → RGB(255,255,255)
```

**圆内点也是纯白** → 原版**没有底色块**（不是"圆角方块"、也不是"圆形 chip"），
就是**纯白背景上的表情字形**，占位 70×70 设备 px。

### 我第一次的判定逻辑是错的（自我拦截记录）

我最初只采了"四角"，看到纯白就判"没有背景"。
**这个推理有缺陷**：若底色是**圆形**（`border-radius: pill`），圆的**四角本就在圆外**，
所以"四角白"**无法排除圆形底色**。改成采"**圆内但非字形**"的点后结论才站得住。
→ 又一次"先下结论、后确认基准"，这次被自己的复核拦住（而不是被审核拦住）。

### conclusion

```
EMOJI_ITEM_BACKGROUND: none（原版纯白背景，无底色块）  MEASURED / 可复算
```

## 十七、C6 升级为**直接测量**并已修正：字号 16px → 24px

上一节（§十六）里，C6 只有"由着色面积反推直径"的**间接**证据，我当时按纪律**不据此改**。
本轮改用更强的方法：**量非白像素的外接矩形**（对实心字形尤其可靠）。

### observation（对 6 个项各自求墨迹 bounding box，设备 px ÷1.75 = CSS px）

```
#1 😂      42x39 设备px → 24.0 x 22.3 CSS px
#2 ?       42x39        → 24.0 x 22.3
#3 💛/❤️   40x40        → 22.9 x 22.9   ← **实心字形，恰好填满 40 CSS px 的盒子**
#4 👀      42x32        → 24.0 x 18.3
#5 😱      38x41        → 21.7 x 23.4
#6 "+1"    35x35        → 20.0 x 20.0
```

我们侧（实测渲染值）：盒 40×40 CSS px、`font-size: 16px`。

### conclusion

在那个最"实心"的字形（#3 爱心）上，**墨迹就跨越约 22.9 CSS px**；
而 16px 字号下 emoji 的墨迹约 14 CSS px。→ **原版字号约 23~26 CSS px**，
故 `16px` 明显偏小，**这是直接测量**（不再是面积反推）。

### implementation impact

`app/src/screens/board.css`：`font-size: 16px → 24px`（取爱心字形反推区间的偏低端，保守）。

### 强度与残余不确定（如实）

- 这是**墨迹外接**的测量，**不是**字体 em 的直接读数：墨迹/em 的确切比例取决于字体实现
  （Noto Color Emoji 的实心字形通常接近满 em，但非 1:1）。
- 因此 **24px 是"据测量得出的最优估计"，不声称是精确复原值**。
- 更精确的做法（本轮未做）：找到原版该 item 的布局/字体尺寸定义，或用一个已知 em 比例的字形反解。
- ⚠ 若 C4 最终裁定"改为图片形态"，本项**随之失效**（届时以图片固有尺寸为准）。

### 为什么本轮敢改而上一轮不敢

上一轮的证据是"**面积比反推直径**" —— 受字形墨迹覆盖率影响，不可靠；
本轮的证据是"**实心字形的墨迹外接矩形**" —— 对实心形状是**直接量纲测量**。
**同一条纪律的两面**：证据不足就不改；证据够就改。
