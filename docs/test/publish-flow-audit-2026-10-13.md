## 初次审核确认的问题（现已修复）

### F02 / P1：发布中的导航绕过保护，失败后丢失当前提交状态

位置：`app/src/screens/PublishScreen.tsx:80`。

复现：填写有效图文并点击发布 → 让创建接口保持等待 → 通过浏览器返回/哈希路由跳转到校园页 → 创建接口随后返回503。

实际：`registerNavigationGuard`因`submitting.current`为真而放行，编辑页卸载，没有继续编辑/保存提示。当前编辑和提交标识没有自动持久化；503失败回到原组件的反馈无法在当前页面显示。补充测试确认离开了发布页，正文输入框消失。

影响：未保存的新编辑会丢失；有旧草稿时只能恢复旧状态。如果原创建请求实际成功但结果未知，重新进入并提交会生成新的请求标识，存在重复发帖风险。本次验证了状态丢失，未在此分支实际制造第二条重复帖。

建议：区分成功后主动跳转与用户在发布中的导航；发布中阻止离开，或在发送前持久保存编辑及同一次提交标识。结果未确认时恢复后应查询/重试原标识。成功后已有`dirty.current=false`可以作为允许跳转的依据。

### F01 / P2：贴纸重新生成的预览失败后，可误采用上一份结果

位置：`app/src/screens/PublishScreen.tsx:69`及`:204`。

复现：生成并采用有效贴纸 → 重新生成，接口返回可解码但没有可见主体的透明PNG → 预览提示“未识别到主体” → 点击仍启用的“确认采用贴纸”。

实际：新的渲染开始时未清空`sticker`，失败时只设置错误，仍保留上次成功的结果；采用按钮仅依赖`!sticker`和`rendering`，渲染结束后可点击。补充测试确认旧预览地址未变，点击采用后发布按钮启用。

影响：用户看到本次处理失败，却能采用并发布上一次结果；“本次预览成功且明确采用”的契约失效。该场景使用人工透明PNG模拟，不说明百度一定返回此类图片。

建议：新渲染开始/失败时清空可采用结果并取消采用状态，绑定结果版本；仅当前版本渲染成功后开放采用与发布。
