# 管理员内容维护方案：活动、校园故事与拍照打卡地

日期：2026-11-21。状态：方案文档，新增能力尚未实施。

## 1. 维护范围与基本关系

管理员主要维护三类整理过的内容：活动、校园故事、拍照打卡地。三类内容都关联已有校园地点，普通用户帖子继续保持现有发布方式，不要求为了地图筛选而新增必选标签。

| 对象 | 解决的问题 | 内容示例（仅作说明） |
| --- | --- | --- |
| 活动 | 什么时候、在哪里、怎么参加 | 摄影征集、校园展览、社团活动 |
| 校园故事 | 这个地方有什么历史、记忆和故事 | 老校门的变化、某栋建筑的校园记忆 |
| 拍照打卡地 | 去哪里拍、什么时间拍、怎么找到机位 | 银杏大道秋景、明湖日落取景点 |

地点是共同基础资料：名称、地址、坐标、简介由「地点管理」统一维护，不在三个栏目各录一份。一个地点可以关联多篇故事、多个活动和一份持续更新的打卡指南。

三类内容与普通帖子分别管理，但可相互引用。例如，管理员可以在银杏大道的打卡指南中关联一条公开帖子作为拍摄示例。引用不改变原帖作者，也不擅自修改原帖正文；匿名内容仍遵守匿名规则。

本方案不要求管理员每天发普通帖子，也不要求给所有历史帖子逐条打标签。

## 2. 当前已有能力与需要新增的能力

以下依据当前仓库的管理中心和 API 客户端核对，指代码能力，不代表新增方案已经上线。

| 能力 | 当前情况 | 本方案处理方式 |
| --- | --- | --- |
| 地点维护 | 已有名称、类型、地址、坐标、简介、历史、启停用和排序等数据；管理更新接口目前未暴露坐标修改 | 复用地点资料；需要纠正坐标时补充明确的管理更新能力，不在其他栏目保存第二份地点坐标 |
| 活动维护 | 已有活动管理、活动投稿审核、时间、关联地点、封面、主办方及外部参与链接等能力 | 复用现有流程与活动实体 |
| 校园故事 | 地点有 `history` 文本，但没有独立故事管理面板 | 新增独立故事条目，支持标题、封面、来源和图文；不能把现有历史文本字段说成已经具备故事栏目 |
| 拍照打卡地 | 已有地点与用户照片，尚无独立打卡指南维护面板 | 新增关联地点的指南资料与发布状态 |
| 普通帖子 | 当前没有本方案所需的用途标签 | 不以普通帖子标签作为故事、打卡栏目的筛选依据 |
| 应用公告 | 代码中已有独立公告发布面板 | 保持独立，用于应用通知，不与活动或故事混用 |

## 3. 管理中心入口

建议在现有管理中心中提供「活动管理」「校园故事」「拍照打卡地」三个入口，继续保留「地点管理」「投稿审核」「内容管理」和「操作记录」。

活动管理直接沿用现有入口；校园故事、拍照打卡地是计划新增入口。第一版可以由同一批现有管理员维护，无需先增加编辑、审核员等新的角色体系。普通用户不能直接发布管理员整理内容。

故事和打卡的用户投稿可在后续复用审核思路，但第一版先支持管理员直接整理。已有活动投稿审核继续使用，不将尚未实现的故事投稿入口显示给用户。

## 4. 活动内容维护

### 4.1 维护字段

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| 标题 | 必填 | 清楚说明活动名称 |
| 关联地点 | 必填 | 从已有且启用的地点中选择 |
| 开始时间 | 必填 | 统一按北京时间输入和展示 |
| 结束时间 | 建议填写 | 填写时必须晚于开始时间；未填写时沿用现有服务端时间推导规则 |
| 活动介绍 | 建议填写 | 说明内容、适合人群及参与条件 |
| 主办方、信息来源 | 建议填写 | 便于核实和后续联系，未知时不编造 |
| 封面 | 建议填写 | 使用真实活动图片，无图片时使用统一占位 |
| 参与方式 | 按需填写 | 目前使用外部链接及介绍，不承诺站内报名功能 |
| 活动类型 | 选填 | 现有字段为自由文本，不直接当作固定枚举筛选 |
| 取消状态 | 管理员维护 | 确认取消后及时更新 |

第一版不因为新文档就把既有选填字段改成服务端必填；可在管理界面提示资料完整度。若后续收紧发布规则，应单独处理历史数据兼容。

### 4.2 发布与更新

1. 管理员录入或审核活动投稿，核对时间、地点、来源与参与方式。
2. 预览活动详情，确认地点和封面正确后发布。
3. 时间、场地或参与链接变化时，修改原活动，避免复制成第二条相同活动。
4. 活动取消时更新取消状态；即将开始、进行中、已结束由服务端按时间推导，管理员不手动指定进行中或已结束。
5. 活动结束后保留历史记录，退出默认进行中/即将开始推荐；历史入口和收藏里的状态沿用现有规则。

现有活动是否要补充草稿、预览或撤回能力，实施时按当前后台实际能力单独安排，不能把故事和指南的新状态直接写入现有活动状态字段。

## 5. 校园故事维护

### 5.1 内容定位

校园故事是管理员整理的独立图文内容，适合承载建筑历史、校园变化、老照片介绍或经过确认的个人回忆。它不等于正文中出现了“回忆”“以前”的普通帖子。

### 5.2 维护字段

| 字段 | 发布要求 | 说明 |
| --- | --- | --- |
| 故事标题 | 必填 | 例如围绕一个具体地点或一段记忆展开 |
| 主关联地点 | 必填 | 从已有地点中选择；第一版先关联一个主地点 |
| 短摘要 | 必填 | 用于地图卡片和故事列表，建议 20–60 字 |
| 正文 | 必填 | 支持段落；第一版可以先采用纯文本和图片，避免直接渲染不受控 HTML |
| 封面与配图 | 按需填写 | 每张图片可附说明、拍摄年份或来源；没有照片时可发布文字故事 |
| 内容来源 | 必填 | 校史资料、公开出处、采访或投稿来源；个人回忆明确标注，不写成确定史实 |
| 故事发生时间 | 选填 | 可写年份或时期；未知时不强行补一个精确日期 |
| 署名/来源展示名 | 按需填写 | 与维护管理员身份分开，不自动将管理员当作原作者 |
| 推荐排序 | 选填 | 只影响故事推荐，不修改用户互动计数 |
| 发布状态 | 必填 | 使用下述新内容状态流程 |

建议的标题、摘要长度是表单编辑指导，接口上线时再统一确定限制并在前后端使用同一套规则。

### 5.3 审校与发布

管理员整理素材 → 保存草稿 → 核对来源和地点 → 预览 → 发布。史实存疑时保留草稿或明确说明不确定性，不能为了填满栏目而补写没有依据的历史内容。

已发布故事修改时，用户端继续显示上一次已发布版本；管理员完成预览并明确发布修改后，用户端才切换到新版本。第一版至少保留发布快照和更新记录，防止草稿中的半成品直接暴露。

来源图片、引用帖子被删除或下架后，相应引用不得继续对外显示；可以保留其余仍有效的正文，管理员修复封面或来源后再发布更新。

## 6. 拍照打卡地维护

### 6.1 内容定位

拍照打卡地是一份关联地点的拍摄指南。第一版建议每个地点最多有一份指南，多个角度和季节放在同一份指南里，避免产生多个同名地图点。用户照片仍保留在原帖子中。

### 6.2 维护字段

| 字段 | 发布要求 | 说明 |
| --- | --- | --- |
| 关联地点 | 必填 | 使用现有地点 ID；地图坐标取地点资料 |
| 推荐标题 | 必填 | 用短句表达看点 |
| 简短推荐理由 | 必填 | 说明值得去拍什么，避免只有“很好看” |
| 示例封面 | 必填 | 至少一张真实图片，或一条有效且可公开引用的带图帖子 |
| 示例图片/关联帖子 | 选填 | 图片需注明来源；帖子保留原作者或匿名展示方式 |
| 建议机位 | 建议填写 | 使用文字说明站在哪里拍；精确机位坐标可后续增加，不能用示例坐标冒充真实位置 |
| 适合时间/季节 | 选填 | 如清晨、傍晚、秋季；未知则不填写，不自动断言当下景色 |
| 拍摄建议 | 选填 | 构图、朝向等简短提示 |
| 开放或临时提醒 | 按需填写 | 例如施工、临时封闭、开放时段；需注明核实时间 |
| 最近核实时间 | 管理员维护 | 与用户帖子发布时间区分，不能显示为“今天有新帖子” |
| 推荐排序与状态 | 按需填写 | 排序、发布、撤回与临时暂停推荐 |

### 6.3 持续维护

管理员先选择地点，再填写指南和选择图片，预览后发布。封面失效、地点停用或拍摄区域临时不可用时及时处理。

季节性内容在对应季节前后检查即可，不要求每日修改。景色已过季时可保留指南并清楚标注适合季节，不能持续写“现在正是最佳观赏期”。临时不适合推荐时暂停该指南，不必停用整个地点。

## 7. 地图筛选与内容的对应关系

本方案修正了早先地图文档中依赖普通帖子用途标签的设想。新增维护能力落地后，地图中的「校园故事」查找已发布故事关联的地点，「拍照打卡」查找已发布且未暂停的指南关联的地点，不根据普通帖子的正文或图片猜分类。

| 地图入口 | 数据来源 | 点开后的主要内容 |
| --- | --- | --- |
| 全部 | 现有可用地点及其公开内容 | 地点概览、故事、指南、活动与相关用户记录 |
| 校园故事 | 已发布的校园故事 | 地点故事列表和故事全文 |
| 拍照打卡 | 已发布且未暂停的打卡指南 | 指南详情、示例图片及相关用户记录 |
| 最近更新 | 对应内容的真实公开发布时间 | 默认仍可沿用近期用户记录；若扩展为综合更新流，需显示内容类型并统一定义时间口径 |

活动继续在现有活动页和地点详情展示；是否在地图顶部增加「活动」入口留待地图实施时确定，本方案不直接增加第五个筛选按钮。

地图卡片分别标注「校园故事」「打卡指南」「活动」「校园记录」，数量也分开统计，例如“2 篇校园故事、8 条校园记录”，不能将一篇故事计成一条普通帖子，也不能把管理员更新指南说成有新用户发帖。

如果只完成地图 UI、还没有故事和指南维护接口，第一版先使用「全部 / 有图记录 / 最近更新」；不显示没有可靠数据来源的故事、打卡筛选。

## 8. 权限、状态与操作记录

### 8.1 权限

现有管理员角色负责维护。隐藏前端入口不算权限控制，所有新增写接口、草稿读取和管理列表都必须在服务端验证管理员身份。

普通用户只能读取当前公开且有权查看的版本，不能通过直接输入详情 URL 读取草稿、撤回内容或管理员内部备注。用户投稿即使以后开放，也不等于直接公开发布。

### 8.2 新增故事与指南的状态

| 状态 | 用户是否可见 | 管理员操作 |
| --- | --- | --- |
| 草稿 | 不可见 | 编辑、预览、发布、删除草稿 |
| 已发布 | 可见 | 编辑工作副本、发布修改、撤回 |
| 已撤回 | 不可见 | 修订后重新发布，保留历史记录 |

打卡指南另设「暂停推荐」标记，区别于地点停用。暂停期间退出地图打卡筛选和推荐；已有详情可显示“暂不推荐”的说明，但不能继续鼓励前往。地点停用时，其故事与指南一律退出地图发现入口，用户详情的可见范围沿用地点现有规则并由服务端统一判断。

这些是新增内容的状态建议，不覆盖既有活动的 scheduled/cancelled 状态，也不改变帖子现有下架逻辑。

### 8.3 操作记录

记录维护管理员、对象 ID、操作类型、时间、必要的修改摘要；发布修改、撤回、暂停/恢复推荐需要能够追溯。撤回已发布内容填写简短原因。第一版不提供无记录的永久删除已发布内容。

图片上传与替换复用现有媒体流程。用户私人媒体不能通过管理员选图变成公开内容；撤回和删除也不能直接删除仍被其他内容引用的媒体文件。

## 9. 管理员日常操作指引

| 时机 | 重点检查 |
| --- | --- |
| 新建内容前 | 是否已有同一地点、同一活动或同一指南，避免重复录入 |
| 发布前 | 标题、地点、图片和来源是否正确，用户预览是否完整 |
| 活动有变动时 | 时间、场地、参与链接、取消状态是否同步更新 |
| 故事收到纠错时 | 核对资料，必要时撤回，修正后重新发布 |
| 季节变化或现场有变化时 | 打卡指南是否过季、封面是否失效、是否需要暂停推荐 |
| 定期整理时 | 失效图片、断开的外链、重复条目、未完成草稿和停用地点关联内容 |

建议先维护少量资料完整、确实有内容的地点，逐步补充。栏目没有内容时显示真实空态，不为填满界面而制造活动、历史故事、图片或互动量。

管理员可见列表建议提供按地点、状态、关键词和更新时间筛选，以及“预览用户端”按钮；发布操作应有处理中和成功/失败反馈，防止连续点击创建重复内容。

## 10. 建议实施顺序

1. 复用现有活动管理与地点资料，整理一份待维护地点清单。
2. 新增校园故事条目及管理表单，先支持文字、封面、图片和来源。
3. 新增每地点一份打卡指南，支持图片、机位描述、季节和暂停推荐。
4. 接入草稿、发布快照、撤回、权限校验与操作记录。
5. 将故事和指南接入地点详情，再接入地图筛选和底部内容面板。
6. 验证用户端、管理端和地图数据一致后，分阶段发布。

后台表单、存储字段和接口路径在具体开发时确定。此文档定义的是业务规则，不表示已经新建了故事表、指南表或相应 API。

## 11. 验收标准

- 活动维护沿用现有活动实体，不重复建立活动库，也不将时间推导状态改成人工状态。
- 管理员可以保存、预览、发布、修改和撤回故事；未发布修改不会提前出现在用户端。
- 一个地点只有一份打卡指南，支持更新、暂停和恢复推荐。
- 地点名称和坐标统一读取地点资料；改名后各入口显示一致，不残留另一份独立地点名称。
- 故事和打卡筛选来自正式维护内容，不依赖不存在的普通帖子标签。
- 地图、地点详情和收藏/分享入口对撤回、暂停、地点停用保持正确反馈。
- 私人图片、匿名身份、草稿和内部备注不会因内容引用而泄漏。
- 发布失败保留表单，重复提交不产生重复条目；发布、修改、撤回与恢复都有操作记录。
- 无数据时如实提示，无来源信息不编造；示意图中的标题、数量和图片不作为正式数据写入。
