## 四、⭐⭐ **核心难点：计数从哪来**（这一节是本计划最要紧的部分）

审核 59 的约束是"**不能简单造数据把 UI 拼成原版**"。而这里有一个**结构性的**困难：

```
「N 条校园圈」按模型应是"该 **学校 × 校区** 下的动态数"（基线已确立这个粒度）。
但我们的 4 条动态的 `school_campus_id` **是 NULL**，而且**无法从现有数据推导出校区**：
   posts.place_id → places.name = "北京交通大学"  ← 这是**学校名**，不是**校区名**
   （基线的校区是 校本部 / 威海校区 / 东校区；我们没有任何字段能区分动态属于哪一个）
⇒ 若直接把它算成"校本部 N 条"，那是**在无证据的情况下给数据编归属** ——
   而迁移 004 的注释明确写了：「未知就表示未知，**不伪造归属**」。
```

因此我**不**在计划里擅自选一个做法，而是把选项摆出来请你裁定（我给出倾向）：

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（我倾向）** | `posts.school_campus_id` **保持 NULL**；顶部下拉照基线做成**校区列表**；「N 条校园圈」在**无法计算时显示为不可用**（而不是 0，也不是编造），并把"校园圈归属未建模"作为**已知数据缺口**登记 | 与基线的**外观不完全一致**（原版每行都有数）—— 但这是**数据缺口**，不是实现缺陷 |
| B | 显式做一次**归属决策**：在种子/文档里记录"本 demo 的单校园圈 = 北京交通大学(校本部)"，并把 4 条动态归到它 | 界面更接近原版；但**前提是承认这是一次"演示性归属决策"**，需要你在文档上明确认可（不能默认） |
| C | 计数按**学校**而非校区算（"北京交通大学 4 条校园圈"），并在 UI 上如实标注粒度 | 偏离基线已确立的"学校 × 校区"粒度 ⇒ 我不推荐 |

**另外两个必须一起裁定的点：**

```
Q1. 可否用**基线里观察到的**学校/校区行做种子？
    · 观察到的：北京交通大学 = 校本部 / 威海校区 / 东校区（三项并列）
    · 这三项既是**原版实测**，也是**现实事实**，且与我们种子用户的 school_name='北京交通大学' 一致
    · 但"种进去"意味着**界面会长得像原版** —— 需要你确认这**不算**"造数据拼 UI"
    （我的理解：**结构与既有证据一致的实体**可以种；**为了好看而填的规模数字**不可以）

Q2. 学校搜索页只有 1 个学校，是否可以接受？
    · 原版那里有很多学校（上海交通大学 2502 条校园圈…），但**那些是原版的生产数据**，
      不是"我们的校园圈"。把它们种进来就是**直接编造规模数字** —— 按你的约束**不做**。
    · ⇒ 结果是：我们的搜索页**内容明显比原版少**，且这是**数据驱动的差异**。
      我建议把它**如实登记**（例如 `SCHOOL_SEARCH_CONTENT_SCALE: DIFFERS_BY_DATA`），
      而**不是**为了对齐外观去种 2502 这种数字。
```
