## 二、这条缺陷为什么重要（而且它的断言是我要求的）

我在委派 WO#2 时的 Gate 断言里明确写了这一条：

> **故意让 media 校验失败 → 断言消息也没写进去**（验证同事务）

因为它对应一个**具体的数据不一致形态**：如果"消息已写入、媒体关联失败"，
库里就会出现一条**在界面里没有图、但确实存在的消息**——
而客户端再渲染时只能显示一条空消息。这类"半写"比直接报错更难发现。

审核对这条的要求也一直是：**消息与 message_media 必须同事务**
（我在工作单里写的原话："事务性：消息与 message_media 同事务（否则会出现
'消息存在但图挂了'或反之）"）。

**现在的实测证明：这条约束没有被满足。**

## 三、定位方向（尚未定位到具体行，下一轮做）

`server/src/index.ts` 的 `POST /api/threads/:id/messages`（子代理新改的段落）。可能形态：

1. **校验发生在 INSERT 之后** —— 先插 messages，再校验 mediaId，失败就返回 4xx，
   但没有回滚/根本没开事务；
2. **只有部分路径在事务里** —— 例如"mediaId 格式非法"在参数解析阶段就返回（不写），
   而"media 不存在/非 private/非 owner"发生在 INSERT 之后；
3. **事务边界写错** —— `begin`/`commit` 的位置与实际写入点不匹配。

脚本报"期望 2 条、实际 3 条"，说明有**一条**失败请求留下了行；
而通过的 A1（合法请求）也是 1 条，所以总共 3 条 = 1 合法 + 2 非法中漏了 1 条。

## 六、修正：我在本节初稿里把结论下得太快，特此更正

我最初把标题写成"**发现真实缺陷**"。**这是过度结论，已改正。** 理由如下。

我把断言原文读出来后，情形是：

```bash
# 成功的只有 A1 一条图片消息 + T1 一条文本消息 = 2
MSGS1="$(PSQL "select count(*) from messages where thread_id='$THREAD'")"
[ "$MSGS1" = "2" ] && ok "会话内恰好 2 条消息（全部媒体校验失败都没写入）" \
  || bad "期望 2 条，实际 $MSGS1 条 —— 存在「校验失败却写了消息」的路径"
```

"实际 3 条"有**至少两种**解释，而它**没有区分**：

| 假设 | 含义 | 性质 |
|---|---|---|
| **H1 产品缺陷** | 某条**校验失败**的请求确实写入了 messages 行（校验在写入之后 / 缺事务） | PRODUCT_DEFECT |
| **H2 测试工件问题** | 例如：A1 被发了两次；脚本用了**固定 thread id** 且**只在末尾清理、开头不清理**，于是有残留；或某次请求实际是成功的 | GATE_DEFECT |

**我倾向尚不能判**：脚本的"Z. 清理"在**末尾**执行，并未在**开头**断言会话起始为空 ——
所以"3 条"完全可能是脚本自身产生的（重复发送或残留），而不是产品的半写。

关键旁证：同一次运行里 **`message_media` 恰好 1 行（PASS）**。
若 H1 成立（失败请求写了 messages 行），那一行大概率**没有** message_media 关联
（否则计数应是 2）——这与"半写"形态一致；但也与"某条纯文本请求成功了两次"一致
（文本消息本来就不带 media）。**两种假设都与观测一致**，因此不能据此定性。

## 八、静态读码决定性结论：**H1（产品缺陷）被否证**

我读了 `server/src/index.ts` 里该 handler 的实际控制流（行号来自当前源码）：

```
1572: await client.query('begin')
1597: // 校验 mediaId（全部通过才写；任一条不过 → rollback + 4xx，一行都不写）
1605: if (mediaId !== null) {            ← 校验块
1612-1614: media_not_found  → rollback + return 404
1619-1621: media_not_private → rollback + return 400
1627-1629: media_not_owned  → rollback + return 400
1634: insert into messages (...)        ← **在所有媒体校验之后**
1647-1650: insert into message_media (...)   ← 仅当 mediaId 非空
1653: await client.query('commit')
1657: catch → rollback
```

而**形状类检查（`bad_media_id`：数组/非字符串/格式错；`media_requires_image_kind`）
全部发生在 1572 的 `begin` 之前**（1553-1566），因此那些路径**根本不在事务里、也不会写任何行**。

**结论**：
- 所有媒体**语义**校验都在事务内、且在 `insert into messages` 之前；失败一律 `rollback`。
- 因此**不存在"H1：校验失败却写了消息"的产品路径** —— **H1 否证**。
- **H2（测试工件问题）成为主要解释**：那第 3 条消息来自脚本自身
  （重复发送、上一轮残留、或脚本里另有一条成功请求）。

## 十二、进一步收窄：脚本只发了 8 次 POST，数量上没有"多发"

因此"实际 3 条"只剩两种可能：

| 假设 | 含义 | 需要什么证据 |
|---|---|---|
| **H2a 某次"预期失败"实际成功** | 例：A3 用的"别人的 media"其实不存在 → 走了 `media_not_found` 分支（仍 400，不写行，排除）；**或** A6 的 `kind≠image` 检查在 shape 阶段就返回（也在 begin 前，排除）…… 需要在运行中看每次的实际状态码 | 打印 8 次调用的**实际 HTTP 状态码** |
| **H2b 会话起始就不为空** | 该 thread 在脚本开始前已有消息（例如 `$THREAD` 是**固定 id**、且此前某次运行残留；或会话创建逻辑复用了已存在的 thread） | **开头断言 `count(*)=0`** |

**注意**：我先前把 H2 描述成"重复发送/残留"，现在收窄为 H2a/H2b 两支。
**两支都属 GATE_DEFECT 范畴**（脚本自身或环境），但我**尚未证认是哪一支**——
因为静态读码只能排除 H1，不能排除 H2a 与 H2b。

## 十四、**推翻我 §八 的结论**：H1 成立，缺陷是"数组形式未被拒绝"

我读了完整证据文件（`docs/pending/m5/evidence/message-media-20260921-181822.txt`），找到了那第 3 条消息的来源：

```
=== A7. **传数组 mediaIds[] / 非字符串 mediaId → 400 bad_media_id**（修订 1 的核心）===
FAIL mediaIds[] 被**静默忽略**并发出了消息
     ({"id":"b01a53b8-…","kind":"image","mentions":[],"mediaId":null})
     —— 不允许：客户端以为发了图
PASS mediaId 非字符串 → 400
PASS 错误码明确 bad_media_id
```

### 结论：这是**真实的产品缺陷（PRODUCT_DEFECT）**

- 客户端传 **`mediaIds`（数组）** 时，服务端**没有拒绝**，而是把它当普通消息**写入了**；
- 产生的消息是 `kind:"image"` 但 **`mediaId:null`** —— 即 **"客户端以为发了图，实际发出一条没有图的消息"**；
- 那第 3 条消息就是它（基线 0 + A1 的图消息 + T1 的文本消息 + A7 这条 = 3 条，但 A1/T1 之外多出的正是这条）。

**这直接违反审核的强制修订 1**（原话："API 用单数 mediaId，不是 mediaIds[]，因为当前没有证据支持一条消息多图"；
我在工作单里也写明"**刻意不接受数组（mediaIds/[id] 一律 400 bad_media_id）**"）。

### 我 §八 的推理错在哪（必须记录）

我在 §八 用静态读码看到：**媒体语义校验全在事务内、且先于 INSERT** —— 这部分是对的，
由此我得出"H1 否证"。**但那个推理有一个隐含假设**：我假设"所有应被拒绝的请求都会进入那条校验路径"。

实际上 A7 的**形状检查**（数组/non-string）**根本没生效** —— 于是请求**从未进入任何校验分支**，
直接按"普通消息"写入了。**我的静态读码只看了"校验之后"的路径，没验证"校验本身是否会被走到"**。

→ 这是同一模式的**第五次**（先下结论、后补证据）：我把"我看到校验存在"等同于"校验会生效"。

### 待定位（下一轮）

`server/src/index.ts` 约 1540–1570 的 mediaId 形状检查段。可能原因：
1. 检查用的字段名/形状与请求实际不符（例如只查了 `mediaId` 是否为数组，而 `mediaIds` 被读作普通字段）；
2. 该段检查位置在某条 early-return 之后，被跳过；
3. 部署产物与实际源码不一致（需核对 dist 里是否有该检查）——**这一条必须最先排除**，
   因为本项目已经栽过"验的是旧产物"两次。

### 影响面（要说清，不只修一处）

A7 那条**静默成功**的路径还有一个副作用：**写入了一条 `kind='image'` 但无 media 的消息**。
这类消息在客户端渲染时会变成"一条没有图的图片消息"——与 M5 追求的"发图闭环"直接冲突。
所以修复不仅要"拒绝数组"，还要确认**不存在其它"kind=image 但无 media"的合法写入路径**。
