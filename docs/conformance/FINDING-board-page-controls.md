## 三、conclusion（逐条，含强度）

| # | 事实 | 强度 |
|---|---|---|
| C1 | 顶部**同时存在返回（`iv_back`）与关闭（`ivClose`）两个控件** | strong（控件 id 直接可见） |
| C2 | 页面存在**留言总数**控件 `tvTotalComment` | strong |
| C3 | 页面存在**下拉刷新**容器 `refreshLayout` | strong |
| C4 | 表情项内部是 **`emotion_image`（图片）**，不是文本字形 | strong |
| C5 | `content-desc` 全空 | strong（全树扫描） |
| C6 | 可见文案集合 = {留言, 仅双方可见, 可以给同学留言噢, 留言仅双方可见} | strong |

### C4 解释了一个悬案

此前 `EMOJI_CHARACTERS` 一直记 `NOT_CAPTURED`，我当时的解释是"可访问性树里没有表情字符"。
**现在有了结构性原因：表情本身就是图片（`emotion_image`），不是文字。**
所以：
- 想拿到具体表情**不可能靠 dump**，只能靠**读图片资源**或**人工辨认截图**（后者属弱证据）；
- 这也意味着**我们的实现用文字 emoji（`😂` 等）在形态上就与原版不同** ——
  原版是**图片**。这是一个新发现的、可复算的差异。

### 处置建议（本轮只登记，不实现）

- 四项都是**可复算**的差异（有原始产物），符合"可驱动实现"的门槛。
- 但**不要一次性全做**：其中 C3（下拉刷新）涉及数据刷新语义、C2（计数）涉及计数口径
  （是留言总数还是双方各自的条数？**dump 只能证明"有这个控件"，不能证明口径**）——
  口径不清就实现，属于**用存在性冒充语义**。
- 下一轮应针对 C2/C3 **再取一次只读观察**确定口径（例如进入一个有留言的账号看这个数字），
  再决定怎么实现。
- C1（返回按钮）与 C4（图片表情）口径清楚，可优先做。

## 十一、C1/C2 的只读观察结果 —— **推翻了我自己 finding 里的两条**

审核记录 23 要求：C1（返回按钮）、C2（留言总数）"先补只读证据再改产品"。
本轮做了只读观察（deep link 进入 + dump + 只读点击 + dump），**结果否证了我原先的两条结论**。

### raw_evidence（本轮新入库）

- `docs/original-baseline/raw-dumps/board-ivback-before.xml`（点击前）
- `docs/original-baseline/raw-dumps/board-ivback-after.xml`（点击后）

### 观察 1：`iv_back` 与 `ivClose` **不是两个按钮**

```
iv_back   bounds=[28,77][98,147]   clickable=**true**
ivClose   bounds=[42,91][84,133]   clickable=**NOT-clickable**
```

`ivClose` 的矩形**完全落在 `iv_back` 内部**。即：
**很可能是"一个可点击容器（id 叫 iv_back）+ 内部图标（id 叫 ivClose）"**，
而不是我原先写的"顶部同时有返回与关闭两个按钮"。

→ **我原先的 C1「缺返回按钮」描述不成立**（至少"两个按钮"这半句是错的）。

### 观察 2：`tvTotalComment` 的文本是**「留言」**，不像计数

```
tvTotalComment  bounds=[0,207][1080,269]  clickable=false  text='留言'
```

它的可见文本就是页面标题「留言」（其下另有「仅双方可见」）。
所以 `tvTotalComment` **很可能不是"留言总数"**，而是**标题区**。

→ **我原先的 C2「原版有留言总数控件、我们缺计数」很可能不成立**。

### 观察 3：点击 `iv_back` 中心 (63,112) 后**页面无变化**

```
点击后 topResumedActivity 仍是 com.kairuotu.campus/...MessageBoardActivity
页面文字仍为：留言 / 仅双方可见 / 可以给同学留言噢 / 留言仅双方可见
```

**不能据此判断按钮语义**：本次是用 deep link 直接进入该页的，
它可能是任务栈的根，因而"返回/关闭"没有可去之处（或会直接退出 App）。
要判定语义需要**从真实入口进入**（例如 更多 → 留言板），那需要额外一次只读导航。

### 这三条观察的结论

| 原结论 | 现状 |
|---|---|
| C1 缺返回按钮（原版有返回+关闭两个） | **撤销"两个按钮"**；"是否有独立返回"**待真实入口观察** |
| C2 缺留言总数 | **撤销**（`tvTotalComment` 文本是标题，不像计数） |
| C3 缺下拉刷新 | **保留待查**（`refreshLayout` 是个大容器 [0,333][1080,1690]，形态像下拉刷新包装，但**语义未证实**） |
| C4 表情是图片非文字 | **保留**（`emotion_image` 直接可证） |

### 这正是审核那句原则的实证

> **不要把 `resource-id` 的名字当成行为 contract。**

`tvTotalComment` 这个名字让人以为是"总数"，实际文本是**标题**；
`ivClose` 这个名字让人以为是个"关闭按钮"，实际可能是**容器内的图标**。
我上一份 finding 正是**照名字写结论**才出了这两个错 ——
本项目的 Gate 原则（结论必须可追溯到可复核产物）在这里又救了一次：
因为我说不出这两个"控件"的**行为**，只能说出它们的**名字**。

### 处置

- **不改产品**（原计划要做的"补返回按钮""补计数"两条，前提已被否证）
- C1 若要继续，需**从真实入口**再做一次只读观察（确定栈关系与返回目标）
- C3 若要继续，需观察滚动/下拉交互（只读交互，且**不制造留言**）

## 十二、C3（下拉刷新）只读观察结果：**不确定，且可能受策略阻断**

审核记录 23 对该项的要求是："拉动刷新通常属只读交互，但要确认**没有其它副作用**；
只观察刷新 UI、列表和网络读取即可，**不制造留言**。"

### raw_evidence（本轮新入库）

- `docs/original-baseline/raw-dumps/board-refresh-before.xml`
- `docs/original-baseline/raw-dumps/board-refresh-mid.xml`
- `docs/original-baseline/raw-dumps/board-refresh-after.xml`

### 观察（一次安全区下拉手势）

手势位置：`input swipe 540 900 → 540 1500`（y=900 落在 `refreshLayout` [0,333][1080,1690] 内，
**远离 y≈1711 的输入行与 y≈1781 的发送按钮**，避免误触写操作控件）。

结果：**没有任何可观察变化**

```
刷新前 id 集合 == 刷新中 id 集合 == 刷新后 id 集合（完全一致）
页面文字始终为：留言 / 仅双方可见 / 可以给同学留言噢 / 留言仅双方可见
前台始终是 MessageBoardActivity
```

### 结论：**NOT_EVALUATED（本次观察不确定）**，不是"否证"

**不能说"原版没有下拉刷新"**，因为：

1. 当前页面处于**空态**（「可以给同学留言噢」），**无可滚动内容**；
   而下拉刷新在无内容时**通常被禁用**；
2. 刷新指示器可能**根本不出现在可访问性树里**（只影响屏幕像素，不影响控件树）；
3. 我的手势参数（起点/时长）也可能不足以触发。

把"没观察到变化"当成"没有这个功能"，**正是本项目一直在防的过度声明**。

### 一个更重要的判断：这一项**可能受策略阻断**

要观察到下拉刷新，最可靠的方式是**在非空留言板上**做（有留言时才有"刷新"的意义）。
但要在**原版**里造出非空留言板，就必须**发一条留言** —— 那是**写操作**，
属于用户明令禁止的行为。

因此：

```
C3 下拉刷新: NOT_EVALUATED
  现状证据: 空态下一次安全区下拉手势无可观察变化（不确定，非否证）
  可达性: 若需要"非空留言板"才能评估，则该项**无法通过合规手段评估**
          → 应在 Gate 里记为 **BLOCKED_BY_POLICY**（而不是"未做"或"通过"）
  例外: 若原版当前账号**本来就有**留言（无需我们写），则可只读观察 —— 需先核实
```

**这正是用户那条硬约束的直接后果**：有些一致性项在合规前提下**根本评估不了**，
它们应当被记成 `BLOCKED_BY_POLICY`，而不是被含糊地留在待办里或默认通过。

### 处置

- 先核实"原版当前账号是否本来就有留言"（**纯只读**：dump 看 `tvNoComment` 是否消失、
  `layout_comment_board` 下是否有便签节点）。若有 → 可继续只读观察；
  若无 → 本项按 **BLOCKED_BY_POLICY** 结案，并写进 Gate 口径。
- **不改产品**（连"是否有这个功能"都未确证，谈实现为时过早）。

## 十三、C3 结案：**BLOCKED_BY_POLICY**

上节留下的核实项（"原版当前账号是否本来就有留言"）**已由本轮已有产物回答**：

`docs/original-baseline/raw-dumps/board-refresh-{before,mid,after}.xml` 三份 dump 中，
**都包含空态文案 `可以给同学留言噢`**（`tvNoComment` 存在、可见），
且 `layout_comment_board` 下**没有任何便签节点**。

→ 该 deep link 进入的留言板是**空态**，因此：

1. **下拉刷新在空态下本就可能被禁用**，无法据此判定"有没有这个功能"；
2. 要造出非空留言板，必须**发一条留言 = 写操作 = 用户明令禁止**；
3. deep link `campusx://messageBoard` **不带参数**，我们无法选择"与某某之间已有留言"的那一对。

**结论**：

```
C3 下拉刷新: BLOCKED_BY_POLICY
  原因: 该断言需要一个**非空留言板**才能评估；而获得该状态只能靠写操作（发留言），
        或依赖"原版账号恰好已有留言"这一我们无法控制的条件。
  已做过的合规尝试: 空态下一次安全区下拉手势（无可观察变化，**不足以判定**）
  Gate 口径: 记为 BLOCKED_BY_POLICY（**不是**"未做"、**不是**"通过"、**不是**"失败"）
```

### 为什么这条结案方式是正确的

用户的硬约束要求：**"凡是必须做一个写操作才能拿到证据的场景，一律记为
BLOCKED_BY_POLICY，不得执行、不得绕道，并如实写进报告与 Gate 判定。"**

本项目此前的 Gate 里已有同类项（点赞切换、发布后反馈、媒体发送过渡）。
C3 属于**同一类**：不是我们偷懒没做，而是**合规前提下做不了**。
把它写成"待查"会让人以为迟早能查；写成"通过/失败"则是编造结论。

### C1–C4 的最终状态

| 项 | 最终状态 | 依据 |
|---|---|---|
| C1 顶部按钮 | **撤销**（原"两个按钮"描述被观察否证）| `board-ivback-{before,after}.xml` |
| C2 留言总数 | **撤销**（`tvTotalComment` 文本是标题）| 同上 |
| C3 下拉刷新 | **BLOCKED_BY_POLICY** | 空态 + 造非空需写操作 |
| C4 表情是图片 | **成立（DEVIATION）**，实现方式待裁定 | `emotion_image` + 裁切图 + 像素测量 |

即：**四条里两条是我写错的、一条合规做不了、一条真的成立** ——
这个比例本身就是"不先观察就实现"风险的量化说明。
