# 纪律：设备端验证进行中时，不要重装 APK / 不要动同一个 WebView

> 记录时间：2026-09-21 17:55（Asia/Shanghai）
> 起因：我自己在写这段时差点犯这个错 —— 我刚改完 `board.css`，本能地想"顺手 rebuild+install 到设备上看效果"。

## 危险动作（会破坏并行验证）

当有一个**设备端验证正在运行**（例如子代理正在跑 `device-login-helper` + CDP 断言）时，
以下动作会**让它的结论失效，甚至直接把它打断**：

1. **`adb install -r <apk>`** —— 会替换包，正在运行的 App 进程被杀
2. **`adb shell am force-stop com.campusx.demo`** —— 同理，会切断 CDP 会话
3. **重新构建 web 产物并 `cap sync`** —— 若之后 App 重启，加载的就是**新代码**，
   于是"验证的是哪一版"变得不确定
4. **在同一台设备上用 CDP 连同一个 WebView 做别的操作** —— 会与它争夺同一条 CDP 连接
   （本项目同一条 CDP 只能有一个控制者：`adb forward tcp:9222` 是全局的）

## 为什么这条重要（与已有纪律同源）

- 它和"**改了代码但验的是旧产物**"是**同一类风险的镜像**：
  那边是"验了旧产物"，这边是"**把我的新产物塞进别人正在验的过程里**"。
- 它也和 `git add -A` 那次的教训同源：**有并发执行者时，模糊/未协调的动作会互相污染**。
  只是那条发生在 git 层，这条发生在设备层。

## 正确做法

| 场景 | 做法 |
|---|---|
| 有设备验证在跑，我要改前端代码 | **可以改、可以提交**（改文件不影响设备）；**不要** build/install/force-stop |
| 我要在设备上验证我的改动 | **等**在跑的那一个结束并汇报，再动设备 |
| 我需要立刻验证、且不能等 | 明确记录"我打断了 X 的验证"，并**让对方重跑**——不能悄悄覆盖 |

## 本次的处置

我改了 `board.css` 并提交（`6ac93aa`）——**这没问题**。
但我**没有** rebuild/install APK，也**没有**用 CDP 连设备去量渲染结果，
因为 `Third-account board isolation` 子代理正在做设备端验证。
**我的 CSS 改动因此处于"已提交但未在设备上目视确认"的状态** —— 这一点必须在
它的验证结束之后补验，不能默认"构建通过就等于渲染正确"。
（构建通过只说明语法没问题；几何是否真的更接近原版，需要设备上实测。）
