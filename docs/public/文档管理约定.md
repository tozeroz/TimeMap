# 文档管理约定

本约定用于统一 TimeMap 项目文档的存放、提交和维护方式，方便团队查找资料，减少重复和过期文档。

## 目录与归类

文档按用途和共享范围归类，不按是否由 AI 生成归类。

| 目录 | 存放内容 | 示例 |
| --- | --- | --- |
| `docs/public/` | 团队共同使用、需要长期维护的正式文档 | 项目代码目录映射、需求与设计文档、数据库结构、接口说明、模块维护说明、本约定 |
| `docs/test/` | 需要共享和保留的测试文档 | 测试计划、测试用例、测试操作说明、验收报告 |
| `docs/<姓名或统一缩写>/` | 个人负责模块的分析、草稿和工作记录 | `docs/zwf/` 下的模块代码阅读笔记、AI 辅助分析、实现过程记录 |
| `docs/local/` | 无需提交到仓库的本地资料 | 临时草稿、AI 对话导出、原始测试输出、临时日志和截图 |

个人目录使用本人名字或团队能识别的固定缩写，避免同一个人使用多个名称。需要时可在以上目录内按模块建立子目录。

AI 生成的文档由使用者核对内容并负责维护。模块的正式设计、接口和维护说明应放到 `docs/public/`；个人分析和未确认的草稿放到个人目录。个人资料成为团队正式参考资料时，应整理后移入公共目录，并更新相关链接。

测试报告中需要长期保留的证据，应随报告放在 `docs/test/` 对应子目录并说明用途；临时测试产物放到 `docs/local/`，避免混入正式测试文档。

## 提交与忽略规则

- 公共文档和正式测试文档原则上提交到仓库。
- 个人目录不默认整体忽略。有协作价值、需要共享或评审的个人资料可以提交；无需共享的资料放到 `docs/local/`。
- 在仓库根目录的 `.gitignore` 中统一忽略 `/docs/local/`。其他无需提交的产物按明确路径补充忽略规则，避免使用覆盖整个 `docs/` 或全部 Markdown 文件的规则。
- 已被 Git 跟踪的文件不会因加入 `.gitignore` 而自动停止跟踪。后续整理时，如需取消跟踪，应确认文件不再需要共享，再单独处理，并保留需要的本地副本。
- 提交前检查本次文档变更，避免夹带临时输出或无关资料。

## 命名与维护

- 文件名应表达主题，例如 `数据库设计.md`、`消息模块维护说明.md`；避免 `新建文档.md`、`最终版2.md` 等难以辨认的名称。
- 持续更新的文档保持固定文件名，用 Git 历史记录版本；阶段性报告或记录可在文件名中使用 `YYYY-MM-DD` 日期。
- 正式文档建议在开头注明负责人、最近更新日期和适用模块；未完成或待确认的内容明确标注为草稿。
- 谁负责模块，谁负责维护对应文档。代码目录、接口、数据库结构或业务行为变更时，同步更新相关说明。
- 移动或重命名文档时，检查并更新引用它的链接；相同主题尽量保留一份正式文档，其他位置通过链接引用。
- 过期资料应更新、删除或明确标注已失效；仍有历史价值的资料可放入对应目录的 `archive/`，并链接当前有效文档。

## 文档入口与后续整理

后续整理时，在 `docs/README.md` 中说明目录用途，链接本约定以及主要公共、测试文档。新增重要文档时同步维护入口。
