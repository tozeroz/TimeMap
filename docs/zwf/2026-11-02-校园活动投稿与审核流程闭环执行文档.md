## 1. 交付目标

负责人需要完成前端、后端、数据库迁移、管理员审核入口、权限、联调和验证记录。完整路径是：

**活动页橙色加号 → 登录／填写表单 → 提交审核 → 我的提交查看记录 → 管理员审核 → 通过后公开展示；未通过则展示原因 → 修改后重提 → 再次审核。**

完成标准：用户提交能持久化，管理员有实际可用的审核页面，用户能看到真实结果，审核通过的活动能在公开列表、详情和对应地点活动区访问。只完成静态页面、模拟接口或手动修改数据库状态均不能视为闭环交付。

## 3. 本轮业务范围

必须交付：

- 普通用户提交活动；名称、地点、开始时间必填。
- 本人查看全部、待审核、已通过、未通过投稿及单条内容。
- 管理员查看投稿，审核通过或填写原因驳回。
- 通过时生成一个关联公开活动；未审核内容不进入公开读取链路。
- 未通过投稿可修改重提；保留历次提交版本和审核记录。
- 登录校验、所有权校验、媒体校验、失败重试、防重复和并发控制。

本轮不扩展：待审核投稿编辑/撤回、已通过活动的作者编辑/撤回、站内报名/支付、强制实时推送。管理员原有活动录入继续工作，不强制改走学生投稿流程。已结束活动能否投稿等新增业务限制不能自行添加；本轮只要求合法时间与结束晚于开始。

## 4. 状态流转及关键规则

建议技术状态为 `pending / approved / rejected`，中文分别是待审核、已通过、未通过。它们与公开活动的即将开始、进行中、已结束、已取消分开管理，不能共用一个 status 字段混装。

| 当前状态 | 操作者与动作 | 结果 | 公开结果 |
| --- | --- | --- | --- |
| 尚无投稿 | 用户提交有效表单 | 创建版本 1，pending | 不公开 |
| pending | 管理员通过当前版本 | approved，记录审核人/时间 | 生成并关联唯一公开活动 |
| pending | 管理员填写原因驳回 | rejected，保存原因 | 不生成公开活动 |
| rejected | 本人修改后重提 | 版本加 1，pending | 仍不公开 |
| approved | 本人查看结果 | 状态不变 | 进入关联公开活动详情 |
| 非 pending | 管理员提交旧审核操作 | 冲突反馈，刷新详情 | 不重复创建或覆盖新结果 |

规则：

- 重提沿用同一投稿 ID，新增版本和历史，不把上一轮审核原因覆盖后永久丢失。当前 pending 展示本轮状态，历史原因可在详情查看。
- 管理员审核必须指定自己看到的版本；如果已被其他管理员处理，返回冲突，不执行“最后一次写入覆盖”。
- 同一投稿最多对应一个公开活动。审核通过与公开活动写入同一数据库事务，任一步失败均不留下半成功状态。
- 公开活动的提交者和审核者分别记录。核实现有 `created_by` 语义后明确映射，不把审核管理员错误显示为活动投稿人。
- 审核时再次校验地点启用、媒体有效等条件；地点失效时阻止通过并给出可恢复的说明。
- 已通过活动以后结束或取消，不改变投稿的“已通过”。若被下架或不可访问，“我的提交”按实际情况提示，不永久写死“已公开展示”。

## 5. 字段与数据库建议

业务字段沿用已有活动命名：`title`、`placeId`、`startsAt`、`endsAt`、`description`、`coverImageId`、`organizer`、`source`、`externalLink`、`activityType`。

- title：trim 后必填，最多 60 字；description：选填，最多 300 字；计数方式前后端一致。
- placeId：真实且已启用的地点；不能仅提交可任意编造的地点名称。
- startsAt：合法时间；endsAt：可空，填写时严格晚于开始时间。界面统一北京时间，传输使用有时区的 ISO 时间，不依赖服务器本地时区猜测。
- externalLink：非空时仅允许 HTTP/HTTPS。链接校验不要求服务器主动抓取目标网页。
- coverImageId：可空；如有，必须是允许用于此投稿的有效图片媒体，校验所有权或合法授权关联，不能只检查 UUID 存在。
- 主办方、来源、活动类型选填；明确最大长度和空串归一化。活动类型沿用现有开放字段，不自行发明固定分类。

建议新增三类数据：

| 数据 | 最小内容 | 约束 |
| --- | --- | --- |
| 投稿主记录 | id、submitter_id、status、current_revision、published_activity_id、created_at、updated_at | submitter 非空；状态约束；公开活动关联唯一 |
| 投稿版本 | submission_id、revision、完整业务字段、submitted_at | `(submission_id, revision)` 唯一；供审核和历史展示 |
| 审核记录 | submission_id、revision、reviewer_id、decision、reason、reviewed_at | 审核对应准确版本；驳回原因必填；单版本只有一次终审结果 |

也可采用等价结构，但必须满足版本不可混淆、历史可追溯、审核事务一致性。表名及实现细节在最终迁移中明确。按本人时间排序和管理端状态/提交时间查询增加必要索引；有分页时采用稳定排序，时间相同时以 ID 等字段确定顺序。

创建与重提使用请求标识（如 `clientRequestId`），服务端按用户、操作及目标版本约束幂等；同标识同内容重试返回同一结果，同标识不同内容拒绝。不要在网络超时后自动换新标识再次创建。

## 6. 建议接口契约

以下为拟新增接口，并非现有 API。开工时由负责人确定最终路径、请求/响应与错误结构，前后端统一后记录实际版本。

| 接口 | 身份 | 用途 |
| --- | --- | --- |
| `POST /api/activity-submissions` | 已登录 | 创建投稿，返回投稿 ID、版本、pending |
| `GET /api/me/activity-submissions?status=&cursor=&limit=` | 已登录本人 | 本人列表、筛选及分页信息 |
| `GET /api/me/activity-submissions/:id` | 本人 | 当前内容、版本、审核历史、关联公开活动 |
| `POST /api/me/activity-submissions/:id/resubmit` | 本人 | 仅 rejected，携带预期版本、修改内容、请求标识 |
| `GET /api/admin/activity-submissions?status=&cursor=&limit=` | 管理员 | 审核队列 |
| `GET /api/admin/activity-submissions/:id` | 管理员 | 审核内容和准确版本 |
| `POST /api/admin/activity-submissions/:id/review` | 管理员 | decision、reason、expectedRevision、请求标识 |

沿用项目现有错误格式；至少区分未登录、无权限/不可访问、校验失败、记录不存在、状态/版本冲突、服务端失败。枚举和分页结构在客户端定义类型，不让不同页面各猜字段。

所有本人接口从登录会话确定用户，不信任请求里的 submitterId。列表在服务端按用户过滤，单条也校验所有权，不能只在前端隐藏按钮。公开活动接口不返回私有投稿、审核原因和历史。

分页列表需返回可靠的下一页依据；没有完整性依据时，不显示“已加载全部”。状态筛选由服务端执行，不能先取一页“全部”后在前端筛，导致漏记录。

## 7. 封面访问与公开链路

这是实施前必须核实的现有依赖：当前活动封面上传用途按公开媒体处理，不能直接声称投稿封面在审核前已经私有。

负责人需要设计并实现：

1. 未审核封面仅本人及有权限的管理员可读取；复用或扩展现有媒体访问校验，不能让私有媒体 URL 直接被匿名读取。
2. 审核通过后公开活动及封面可被公众正常访问；明确采用权限转换还是生成公开副本，并保证失败可恢复。
3. 投稿版本、当前封面及公开活动引用纳入媒体保留规则，避免清理任务误删仍被使用的图片。
4. 被更换、上传后未提交的封面按已有或新增的清理规则处理；不得清理仍被历史审核记录使用的资源。

公开链路需逐项回归：活动列表 → 活动详情 → 地点活动区 → 从投稿查看活动。选择未来时间的测试活动验证默认列表；已结束活动可能只出现在对应筛选，不能以默认列表不出现就误判审核失败。

## 8. 前端执行任务

| 任务 | 行为与交付 |
| --- | --- |
| 活动入口 | 移除临时 alert，进入真实投稿表单；不进入普通帖子发布；保留活动列表筛选/滚动 |
| 登录返回 | 未登录先登录；成功回到投稿入口；会话过期与返回流程保留未提交内容，不能伪造登录成功 |
| 提交表单 | 按复刻说明完成三个分组、地点、时间、上传、校验、提交和离开确认 |
| 投稿详情 | 本人可查看完整字段、当前状态及历史；未通过展示审核原因，已通过提供活动入口 |
| 我的提交 | 个人主页第三标签、四状态筛选、列表、空状态、分页/重试、状态刷新 |
| 修改重提 | 加载原投稿当前版本和字段，提交成功后进入 pending；不直接在前端改审核结果 |
| 管理员页面 | 复用现有管理入口增加队列与详情；明确通过/驳回，填写原因，展示处理反馈和冲突刷新 |

建议页面路由 `#/activity-submit`、`#/me?tab=submissions`；投稿详情及管理端子路由由负责人统一。当前这些新参数/路由尚未接通，必须注册并实际消费。个人主页键盘切换由两标签扩展成三标签，保留原“我的发布”“我的收藏”及活动收藏功能。

UI 必须覆盖加载、无记录、某筛选为空、网络失败、封面失败、未登录、权限失效。提交中禁用按钮但保留输入；失败不清空。快速切换筛选丢弃旧响应。成功跳转依据服务端返回，不以 timeout 或本地写入冒充成功。

管理员审核 UI 无本次效果图约束，要求清楚、可操作，能看到完整字段、封面、来源链接、提交人、版本、历史和决定。实际操作必须走鉴权接口。

## 11. UI 复刻验收与最终交付
