## 2. 数据库迁移

| 项 | 内容 |
| --- | --- |
| 文件 | `server/src/migrations/031_activity_submissions.sql` |
| 执行顺序 | 排在 `030_user_profiles` 之后；仓库内注册于 `server/src/db.ts` 的 `MIGRATIONS` 数组末尾 |
| 幂等 | 全部 `IF NOT EXISTS` / `CREATE OR REPLACE`，重复执行安全（本地实测连跑两次） |
| 换行 | 纯 LF（部署脚本的 checksum 预检会拦 CRLF） |
| 回退 | 只**新增**表与函数，不改动既有表结构；回退即 `drop table activity_submission_*` 并还原 `can_read_media`（006 的定义在本次迁移里被 `CREATE OR REPLACE` 覆盖过一次，原定义见 `006_media_scope.sql`） |

四张表：

| 表 | 作用 | 关键约束 |
| --- | --- | --- |
| `activity_submissions` | 投稿主记录：归属人、审核状态、当前版本、关联公开活动 | 状态 `pending/approved/rejected`；`published_activity_id` **唯一**（一条投稿最多一个活动） |
| `activity_submission_revisions` | 每轮提交的完整业务字段（不可变） | 主键 `(submission_id, revision)`；`ends_at > starts_at` |
| `activity_submission_reviews` | 某个版本的终审结论 | `UNIQUE (submission_id, revision)` ⇒ 同一版本只能有一次终审；驳回必须写原因 |
| `activity_submission_requests` | 幂等键 | 主键 `(actor_id, client_request_id)` + payload 摘要 |

**为什么审核状态不塞进 `activities.status`**：公开活动的状态是按时间**推导**的展示态
（upcoming/ongoing/ended/cancelled），投稿状态是**流程**状态。一条已通过的活动几周后会变成"已结束"，
但它的投稿仍然是"已通过"——同一个字段装不下两套语义（执行文档 §4 也是这么要求的）。

## 3. 接口（最终采用版本）

全部实现于 `server/src/submissionsRoutes.ts`，在 `server/src/index.ts` 里注册。

| 接口 | 身份 | 行为 |
| --- | --- | --- |
| `POST /api/activity-submissions` | 登录 | 创建投稿（版本 1，pending）；带 `clientRequestId` 幂等 |
| `GET /api/me/activity-submissions?status=&cursor=&limit=` | 本人 | 列表；**服务端**按归属人与状态过滤，游标分页 |
| `GET /api/me/activity-submissions/:id` | 本人 | 详情 + 审核历史 + 关联活动可访问性 |
| `POST /api/me/activity-submissions/:id/resubmit` | 本人 | 仅 `rejected` 可重提；版本 +1，回到 pending |
| `GET /api/admin/activity-submissions?status=&cursor=&limit=` | 管理员 | 审核队列，多带 `submitter` |
| `GET /api/admin/activity-submissions/:id` | 管理员 | 审核详情（含历史） |
| `POST /api/admin/activity-submissions/:id/review` | 管理员 | `decision` + `reason` + `expectedRevision` |

错误口径沿用项目现有格式 `{ error, ... }`，并区分：

- `401 unauthorized`：未登录
- `403 forbidden`：非管理员调用 `/api/admin/*`
- `404 not_found`：**别人的投稿与不存在的投稿返回同一个 404**（不泄露存在性）
- `400 invalid_payload` + `details[]`：字段校验失败
- `409`：`already_reviewed`（已被处理）/ `revision_conflict`（版本对不上）/
  `not_rejected`（非驳回状态不能重提）/ `request_id_conflict`（同标识不同内容）/
  `place_unavailable`、`cover_unavailable`（审核前的可恢复拦截）

### 几条硬规则是怎么落地的

- **幂等**：`clientRequestId` + 内容摘要存进 `activity_submission_requests`。
  同标识同内容 → 返回上次结果（不会重复投稿）；同标识不同内容 → 409。
  并发重放撞唯一键（23505）时，回滚后重新读那次结果并返回。
- **审核并发**：事务内 `select … for update` 锁投稿行，再比对 `expectedRevision`。
  两个管理员同时点通过，只有一个成功，另一个 409 并刷新到真实状态；公开活动不会生成两条。
- **原子性**：审核通过与"插入公开活动"在**同一个事务**里。地点被停用时整笔回滚并提示，
  不会出现 approved 却没有活动的中间态（E10 实测）。
- **作者归属**：`activities.created_by` 写的是**投稿人**，不是审核管理员；
  审核人单独记在 `activity_submission_reviews.reviewer_id`（数据库实测两者不同）。

## 4. 封面媒体的权限与公开策略（执行文档 §7）

| 场景 | 结果 |
| --- | --- |
| 上传 | 新增用途 `activity-submission` → `scope='private'`（写盘到 `uploads/private/`） |
| 审核前，投稿人本人读 | 200 |
| 审核前，管理员读 | 200（审核要看图） |
| 审核前，匿名 / 其他学生读 | **404**（不是 403 —— 连"存在"都不暴露） |
| 审核通过后，公众读活动封面 | 200 |

实现方式：**审核通过时复制出一份 public 副本**（`submissionsRoutes.promoteCover`），
公开活动引用副本，私有原件与作者归属都不动。

选"复制"而不是"把 scope 改成 public"，是因为 `media.storage_key` 与 `scope` 共同决定物理目录
（`uploads/private/…` vs `uploads/public/…`）：只改数据库字段会让文件留在私有目录，匿名请求必然 404。
复制走的是既有的 public 静态下发链路，不需要给私有目录开任何口子。

失败恢复：副本文件与 media 行在同一个事务窗口内写入（沿用 `acquireMediaMutationLock` 的备份一致性锁）；
事务确定回滚时删除已复制的文件；`commit` 结果不确定时不删（宁留孤儿文件，也不破坏已提交数据）。

媒体可读性的判定在数据库函数 `can_read_media` 里（迁移 031 用 `CREATE OR REPLACE` 扩展），
不是散落在应用层的 if —— 这样"未审核内容不进公开链路"不依赖任何人记得过滤。

## 5. 管理员界面（本次新增）

`app/src/screens/AdminScreen.tsx` 新增第 2 个面板「投稿审核」（`data-admin-tab="submissions"`）：

- **队列**：待审核 / 已通过 / 未通过三个筛选（**服务端**参数），游标"加载更多"，加载/失败/空态齐全。
- **卡片**：状态徽标、提交人、提交时间、标题、地点、开始时间、当前版本；已处理的直接显示结果与驳回原因。
- **详情**（展开）：封面缩略图、提交人、地点、起止时间、简介、主办方/类型、信息来源、
  原文链接（可点）、当前版本与提交时间、完整审核历史。
- **审核动作**：通过 / 驳回；驳回必须填原因（前端先拦一次，服务端再拦一次）。
  确认前明确写出"将按第 N 版内容通过/驳回"，避免审错版本。
- **成功反馈**在面板层显示（`data-sub-panel-notice`）：因为处理完的卡片会立刻离开当前筛选列表，
  卡片内的提示会随卡片一起消失，等于没有反馈（这是实测发现的，已修）。
- **冲突**：服务端 409 时提示"已被处理过或版本已变化，已为你刷新"，并重新拉详情 + 队列。

界面没有本次效果图约束，按"审核时能一眼看清完整字段与版本"来做，复用 `adm__*` 既有样式，未新造设计语言。

## 7. 未做 / 已知限制（不夸大）

1. **未推送、未部署**：代码只在本地 `new-mvp` 提交。线上仍是上一版（数据库 29 条迁移），
   部署需要补跑 030 与 031 两条迁移，按团队流程走。
2. **并发验证的边界**：E09 的并发是同一进程内两个请求真实同时到达，验证的是行锁 + 唯一约束；
   没有做多进程/多实例压测。
3. **封面副本的清理**：审核通过时复制出的 public 副本会长期存在；
   投稿被多次重提时，历史版本引用的私有封面不会被自动清理（保留规则未接入清理任务）。
   执行文档 §7.3/§7.4 提到的"纳入媒体保留规则"目前**没有**做，属于已知缺口。
4. **未审核投稿的编辑/撤回**：按执行文档 §3 本轮不做。
5. **管理员原有录入未改**：`POST /api/admin/activities` 保持不变（文档要求不强制走投稿流程）。
6. **UI 复刻评分未做**：执行文档 §11 要求两张参考图各自 ≥80 分并附逐项评分，
   本次由我做的只有管理员界面（该页无效果图约束）；用户侧三页是队友既有实现，
   评分与差异记录需要对照 UI 文档单独完成。
7. **原有 P0 冒烟测试有 4 项失败，与本次改动无关**：合并 `main` 后队友重写了底部 tab 与活动页
   （tab 文案改成 广场/我的、活动页默认查询 `status=all`、列表元素结构变化），
   旧的断言没跟上。已用 git 核对：这 4 项在合并提交（未含本次改动）里就是这样。
   ⚠️ 其中"活动页默认列出全部状态"与 ACT-001 的"默认只看即将开始/进行中"**不一致**，
   需要产品侧确认是不是有意的改版。
