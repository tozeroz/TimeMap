# 私信功能设计与实施方案

更新日期：2026-11-20  
适用模块：公开个人名片、私聊、消息列表、私有聊天媒体  
状态：首版已在本地实现并验证，尚未部署。第 2 节保留设计时的代码基线，实际交付见第 11 节。

## 1. 目标

打通「公开帖子 → 个人名片 → 发私信 → 聊天 → 消息列表继续聊天」，允许此前没有会话的两位用户开始聊天。已有会话必须复用，消息应可靠保存、可重试、可继续加载，用户昵称和头像跟随当前公开资料。

复用现有聊天页、会话表、消息表以及图片和语音媒体授权，不另建一套聊天系统。第一版私信使用用户的公开身份，不提供匿名私信。

## 2. 当前实现与缺口

以下结论来自本次代码检查。

| 模块 | 现状 | 需要补齐 |
| --- | --- | --- |
| `UserProfileScreen.tsx` | 拉取自己的会话列表，按 `kind=direct`、`peerId` 匹配；恰好一个会话才显示私信入口 | 改为通过服务端创建或获取双人会话，无会话时也能发起 |
| `message_threads`、`thread_members` | 支持 direct/group，成员在同一会话内唯一 | 双人用户组合唯一，目前成员唯一约束不能防止重复创建会话 |
| `GET /api/threads` | 返回本人会话、对方 ID/昵称、最后消息 | 空会话过滤、当前头像、未读数、稳定分页 |
| `GET /api/threads/:id` | 已有会话及成员信息查询 | direct 会话统一公开对方资料，不依赖前端猜身份 |
| `GET /api/threads/:id/messages` | 校验成员关系，按创建时间正序取最多 50 条 | 当前会截断为最早 50 条；需改成最近消息、向前翻页和向后增量读取 |
| `POST /api/threads/:id/messages` | 已有文字、图片、语音等消息写入与成员检查 | 发送幂等键、会话内稳定序号、拉黑及频率检查 |
| 私有媒体 | 已有聊天媒体与访问校验 | 继续复用，不能将聊天附件变成公开头像或帖子媒体 |

## 3. 首版交互

### 3.1 从名片发起

- 他人公开名片显示「发私信」；自己的名片不显示。
- 未登录点击后进入登录流程，保留目标用户 ID，登录成功后可返回目标名片继续操作。
- 点击时按钮进入加载态，阻止重复提交。服务端返回真实会话 ID 后进入聊天页。
- 创建失败留在名片，显示错误和重试入口，不生成临时聊天 ID，不跳转其他人的会话。
- 个人名片不再通过拉取全部会话判断是否可以联系。

### 3.2 空会话与首次发送

允许点击时在数据库建立空会话，但空 direct 会话不出现在双方消息列表，不增加未读数、不通知对方。聊天页可显示「还没有消息，打个招呼吧」。

第一条消息成功提交后，该会话才进入双方消息列表。发送者看到自己的消息；接收者在前台刷新或轮询后看到会话与未读数。

仅打开名片或聊天页不发送消息。重复打开空会话仍复用同一个会话；首版不自动删除空会话，避免破坏用户保存的会话链接。

### 3.3 聊天与消息列表

- 聊天页显示对方当前昵称和头像；没有头像或加载失败时显示占位图。
- 打开会话先读取最近 50 条，并按会话序号从小到大显示；向上继续加载更早消息，保持视口位置。
- 接收新消息时，用户已在底部则跟随滚动；正在翻历史时显示「有新消息」，不抢走阅读位置。
- 会话列表按最后一条已提交消息排序，同一时间以会话 ID 排序。文字显示摘要，图片和语音显示类型摘要。
- 未读数量超过 99 显示 `99+`，点击进入后按已展示的消息位置更新已读。
- 重新进入名片、会话列表和聊天页时读取当前公开资料，不能一直使用创建会话时的昵称、头像快照。

### 3.4 发送失败和重试

消息可有「发送中／已发送／发送失败」状态。只有服务端成功响应或增量同步确认同一幂等键后，才标为已发送。

失败保留输入或失败气泡。重试复用原 `clientRequestId`；编辑内容后重新发送属于新消息，必须生成新键。会话切换时草稿按会话保存，防止将 A 的草稿发给 B。

图片、语音继续使用现有上传和发送流程。上传成功但消息未确认时重试原媒体引用，不能每次重新上传；本次不扩大现有媒体大小、类型和访问权限。

## 4. 数据设计

新增迁移编号在实施时按仓库最新清单分配，不修改已应用迁移。以下为拟议字段，需结合当时完整 schema 核对重名及类型。

### 4.1 双人会话索引

新增 `direct_thread_pairs`：

| 字段／约束 | 用途 |
| --- | --- |
| `thread_id`，主键、引用 `message_threads.id` | 对应现有 direct 会话 |
| `user_low`、`user_high`，引用用户 | 对两个用户 UUID 按数据库一致顺序规范化存储 |
| `UNIQUE(user_low, user_high)` | 同一对用户只有一个私聊会话 |
| `CHECK(user_low < user_high)` | 禁止自己与自己聊天，防止顺序颠倒绕过唯一约束 |

在一个事务内创建会话、两个成员和组合索引。并发唯一冲突时回滚本次新建，再查询已经提交的组合记录，返回同一个真实会话；不留下孤立的 `message_threads`。

direct 会话成员固定为索引中的两人。任何现有成员修改路由都必须禁止向 direct 会话添加第三人，不能只保护新建入口。群聊不写组合索引。

### 4.2 消息序号与重试去重

- `message_threads.next_message_seq`：会话内递增计数，初值 0。
- `messages.thread_seq`：正整数序号，`UNIQUE(thread_id, thread_seq)`，用于顺序、分页、增量读取和已读。
- `messages.client_request_id`：客户端消息 UUID；新客户端发送时必填。
- 对非空键设 `UNIQUE(sender_id, client_request_id)`。同一键不能被拿去另一会话或对应另一份消息内容。

发送事务内先检查已成功的同键消息；相同会话和规范化内容返回原消息，不增加序号或未读。键相同但会话、消息类型、正文、媒体或提及信息不同，返回 409。

对于首次写入，在统一锁顺序下锁住会话行、复核成员与拉黑状态、分配序号、插入消息及媒体引用，整体提交。序号分配与写入必须同事务，避免先返回较大序号，之后才提交较小序号而使增量客户端漏消息。

历史消息和旧客户端允许幂等键为空；这不具备重试去重保证，文档与测试须区分。序号对所有写入路径统一分配，不能让旧客户端产生无序号消息。

### 4.3 已读位置

在 `thread_members` 增加 `last_read_seq`，默认 0，表示该成员已确认读到的最大会话序号。

更新采用 `GREATEST(旧值, 新值)`，不允许多设备或迟到请求把位置倒退。序号必须属于该会话且不超过已提交的最大值；不能接受客户端伪造未来序号。

未读数统计：本会话中 `thread_seq > last_read_seq`、发送者不是本人且未撤回的消息数量。历史消息撤回不倒退已读位置；撤回占位仍保留原序号。

### 4.4 拉黑

新增 `user_blocks(blocker_id, blocked_id, created_at)`，用户组合唯一，禁止拉黑自己。

任一方拉黑后，拒绝新建私聊及新的消息写入，包括已经打开的聊天页；已有历史记录仍由原参与者可见。解除拉黑不会删除历史消息。为避免与发送竞态，拉黑变更和发送使用相同的规范化用户对事务锁，取得锁后再检查状态。

## 5. 拟议接口

所有写入只从服务端会话识别当前用户，不接受客户端指定发送者。以下接口均为设计目标。

| 接口 | 输入 | 输出／行为 |
| --- | --- | --- |
| `POST /api/threads/direct` | `{ peerId }` | 201 创建，200 复用；返回 `{ id, kind: 'direct', peer }` |
| `GET /api/threads` | `limit`、`cursor` | 本人有消息的会话分页；增加对方头像、未读数和下一页游标 |
| `GET /api/threads/:id` | 会话 ID | direct 返回统一的 `peer` 公开资料；group 保留原语义 |
| `GET /api/threads/:id/messages` | `limit=50`；可选 `beforeSeq` 或 `afterSeq`，两者互斥 | 最近、历史或增量消息，返回分页边界和是否还有下一批 |
| `POST /api/threads/:id/messages` | 现有消息参数 + `clientRequestId` | 返回真实消息 ID、序号、时间和媒体；幂等重试返回原消息 |
| `POST /api/threads/:id/read` | `{ throughSeq }` | 单调更新已读，返回服务端位置与未读数 |
| `POST /api/users/:id/block` | 无额外作者字段 | 幂等拉黑 |
| `DELETE /api/users/:id/block` | 无额外作者字段 | 幂等解除拉黑 |

`peer` 只包含 `{ id, displayName, avatarMediaId }`。不新增公开手机号、院系、年级等私有字段。

消息响应建议结构：

```json
{
  "threadId": "会话UUID",
  "items": [],
  "olderCursor": null,
  "newerCursor": null,
  "hasMore": false
}
```

初次和历史查询取较新的一段后按序号正序返回；增量查询取 `afterSeq` 之后最早的下一批，按序号正序返回。增量积压超过一页时立即继续取完，不能直接跳到最后一页。所有查询应用成员授权，不能用游标绕过授权。

错误口径：

| 场景 | 建议响应／界面 |
| --- | --- |
| 未登录发起／发送 | 401，进入登录流程 |
| 目标不存在 | 404，提示用户不可用 |
| 会话不存在或不属于当前用户 | 404，不泄露其他人的会话是否存在 |
| 与自己建立私聊、非法输入 | 400 |
| 无法联系（含拉黑） | 403 `messaging_unavailable`，统一提示「暂时无法向该用户发送私信」 |
| 幂等键内容冲突 | 409，不修改原消息 |
| 频率超限 | 429，返回 `Retry-After`，保留草稿 |
| 服务或数据库不可用 | 503，失败态支持重试，不伪装成功 |

已有私有会话接口的状态码兼容策略需在实施时统一审计；不能只修改文字消息路由而遗漏详情、媒体或语音入口。

## 6. 未读与前台同步

第一版采用前台轮询，不承诺后台实时通知或系统推送：

- 当前聊天页可见时每 3 秒增量取消息；消息列表可见时每 10 秒刷新会话摘要。
- 页面隐藏、退出会话、切换账号或注销时停止旧请求。恢复可见时立即同步一次。
- 同一任务不重叠轮询；网络失败逐步退避到最长 30 秒，恢复成功后回到正常间隔。
- 按服务端消息 ID 和幂等键合并，避免发送响应和轮询回包产生重复气泡。
- 会话已打开、页面在前台且最新消息成功展示后，才上报已读。上报位置来自本次实际展示的消息，不能直接把服务端最新序号全部标已读。
- 新消息列表中可有数字徽标，但数据来源必须是服务端；未读同步失败时保留已知状态，不能本地随意清零。

第二阶段再评估 WebSocket／SSE、安卓系统推送、后台通知和多设备同步性能。第一版无需引入独立即时通信服务。

## 7. 匿名与反骚扰边界

匿名帖子和匿名评论不增加跳真实作者主页、发私信或返回真实作者 ID 的入口。用户即使能管理自己的匿名内容，也不能让其他访问者通过页面或接口关联到作者。

私聊入口只接受公开名片的用户身份；匿名帖代号不能当作 `peerId`。本方案不设计「匿名楼主私信」模式。

首版建议可配置频率阈值：每个用户每分钟最多创建 10 个新私聊、发送 30 条消息；同一双人会话每分钟最多发送 20 条。复用已有会话不计入新建次数；幂等重试不重复计消息数。阈值为实施默认建议，应在联调时校准，不是当前已生效限制。

拉黑作为首版能力。消息举报作为第二阶段单独设计：只在举报者主动提交时保留必要消息证据并明确管理权限，不在本次默认开放管理员浏览全部私聊。

## 8. 历史数据迁移与兼容

上线前只读盘点 direct 会话：成员数量、成员有效性、重复用户组合、消息数量、媒体引用及已有消息时间顺序。导出汇总与备份，不能通过随意取第一个成员掩盖异常。

恰好两名有效成员且组合不重复的会话，可回填组合索引。成员异常或重复组合须先形成单独修复清单并审查，不自动删除会话、消息和媒体。唯一约束是上线前置条件，不能绕过失败继续发布。

重复组合确需合并时，应有可回滚的专门迁移：保留所有消息 ID 和媒体引用，确定唯一会话，迁移消息归属并为旧会话链接建立重定向。原成员必须完全一致；重新生成序号并保守处理已读，避免误标已读。这项不能藏在新建接口中临时执行。

历史序号按 `(created_at, id)` 回填，同时间消息以 ID 稳定排序。先使全部消息写路径支持新序号，再开放增量读取。新索引和字段迁移必须在旧数据上验证，不修改旧迁移校验和。

旧客户端无分页参数时的消息读取行为应保持兼容；新客户端显式采用新分页契约，不能在没有更新 UI 时单独把历史正序列表改成最近 50 条。旧客户端没有已读上报时，其已读状态不会被假定已更新。

## 9. 实施顺序

1. **数据盘点与迁移**：备份、检查旧会话，完成组合唯一约束、消息序号、幂等键、已读字段及拉黑表。迁移编号按实施时清单确定。
2. **服务端闭环**：创建／复用会话、统一成员授权与锁顺序、消息去重、分页、已读、频率和拉黑；旧媒体权限测试必须同时通过。
3. **名片入口**：显示「发私信」、登录后返回目标、按钮加载与错误反馈；移除前端遍历会话找目标的逻辑。
4. **聊天与列表**：当前头像昵称、空会话隐藏、历史和增量合并、草稿与失败重试、未读和前台同步。
5. **回归与发布**：本机隔离数据库和两账号联调后，先部署兼容旧客户端的后端，再部署网页。按当前用户决定，安卓打包与发布继续暂停；恢复发布时需由原签名持有者构建。

建议把新的私聊创建、拉黑与消息读写规则拆到独立服务／路由模块，统一公共身份转换和成员授权。实际拆分应保持现有外部 URL，不以重构为由扩大改动范围。

## 10. 验收标准

| 类别 | 必须通过的用例 |
| --- | --- |
| 首次联系 | A 从 B 名片发起，得到真实会话；自己、未知用户及未登录分支正确 |
| 并发唯一 | A 连点、A/B 同时发起、网络超时后重试，最终只有一个双人会话和两个成员 |
| 空会话 | 只打开不发送，不出现在双方消息列表、不产生未读；首次发送成功才可见 |
| 消息可靠性 | 连续重试同键只落一条；不同内容复用键返回冲突；失败保留草稿／媒体引用 |
| 分页与同步 | 超过 150 条消息仍能到达最新并翻完历史；同时间、并发发送、积压多页均无重复遗漏 |
| 已读 | 自己发送不算自己未读；只读到已展示位置；晚到请求、多设备不倒退；撤回口径一致 |
| 资料同步 | 改名、更换和删除头像后，名片、会话摘要、聊天头部及消息作者显示一致 |
| 隔离 | 第三人不能读写会话或访问附件；伪造 sender、游标和未来已读位置均被拒绝 |
| 匿名 | 匿名帖子／评论仍不可联系真实作者，不通过私信 API 新增匿名身份关联字段 |
| 拉黑与限流 | 拉黑后已有聊天页也不能发新消息；解除后恢复；限流可重试且不丢输入 |
| 回归 | 群聊、图片、语音、撤回、媒体授权、退出登录和切换账号不受破坏 |
| 页面 | 320/390/1024 像素、键盘弹出、列表返回和历史滚动锚点正常 |

数据库测试使用独立 schema，不向线上灌入测试私信。验收报告分别记录接口、浏览器和安卓真机结果；安卓尚未测试时明确标注，不能用网页测试替代。

## 11. 本地实现与验证记录

本方案首版已实现，尚未部署，也未进行安卓打包。新增迁移为 `046_direct_messages.sql`，注册在迁移清单中；异常旧会话会使迁移失败并回滚，部署前仍须按第 8 节盘点正式库。不会自动合并重复历史会话。

实际改动：

- `server/src/directMessages.ts`：创建／复用、事务锁、幂等准备、限流、拉黑、序号已读。
- `server/src/index.ts`：会话分页与当前头像、消息最近／历史／增量分页，接入所有消息发送路径；未传 `paginate=1` 的旧消息查询仍保留原协议。
- `server/src/inboxRoutes.ts`：通知中的私信未读同时遵守新序号位置与原有读快照，“全部已读”继续有效。
- `app/src/screens/UserProfileScreen.tsx`、`LoginScreen.tsx`：名片发起、登录后回到目标名片、错误反馈。
- `ChatScreen.tsx`：当前公开资料、历史分页、增量去重、前台同步、新消息提示、可重试草稿和附件、拉黑设置。草稿和未确认请求按账号与会话保存在当前浏览器会话内，离开后重进仍复用幂等键。
- `MessageScreen.tsx`：私聊列表与未读、更多会话、前台刷新；刷新时重取已经展开的页数。
- `app/src/data/useForegroundPoll.ts`：可见页面轮询、单请求、退避、账号隔离；聊天 3 秒、列表 10 秒，后台停止。

会话列表支持可选 `kind=direct`／`kind=group`；消息列表用字符串序号避免 JavaScript 大整数精度丢失。默认限流可通过 `DM_CREATE_PER_MINUTE`（10）、`DM_SEND_PER_MINUTE`（30）、`DM_THREAD_SEND_PER_MINUTE`（20）配置；非法配置回落默认值。这里只说明配置名称，不保存部署凭证。
