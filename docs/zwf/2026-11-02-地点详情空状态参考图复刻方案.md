# 地点详情空状态参考图复刻方案

日期：2026-11-02。参考：《北交大地标详情·空状态.png》。范围：地点详情页面的布局、空状态与配套数据口径调研；本轮不修改页面、接口或线上数据。

## 结论

现有地点详情已经具有基础资料、校史与老照片、近期活动、帖子排序、筛选、查看全部和预选地点发布等能力。可以沿用页面和路由重做样式，纯视觉难度中低。

用户于2026-11-02明确：北京交通大学是现有具体地标的父地标，用于地图缩小后的聚合展示，目前不应纳入普通地点详情。参考图中的学校名称只用于视觉参考，实际普通详情应展示明湖、图书馆等子地标。

本方案按此修订：普通地点详情的视觉改造与空状态纠正是本页范围；父地标的缩放显隐及点击分流属于地图模块，不新增学校总览详情页。

## 页面结构与视觉

建议页面结构为：

1. 导航栏。
2. 地点介绍：分类、名称、地址、简介、地图入口、可选装饰。
3. 校史与老照片。
4. 近期活动。
5. 地点内容：筛选/全部、排序、有内容或相应空态。
6. 热门说明折叠区。
7. 独立底部发布栏。

使用既有米白背景、深蓝文字、品牌橙装饰与全局间距变量。分区以细分隔线和留白组织；主按钮继续采用对白字更清晰的深橙色，而非机械复制参考图中的浅橙渐变。

地点大标题建议约28–32px，分区标题约18–20px，正文和操作约14–16px，辅助文字约13px。校门装饰不能挤压标题和地址，可在窄屏缩小或隐藏。系统状态栏与手势条继续使用既有 Shell/原生处理，不作为网页内容重画。

普通地点未必适合校门图形：学校级地点可用校门装饰，具体地点使用通用地点装饰或不显示。不要凭“北京交通大学”这类名称判断类型；如需按学校/区域/具体地点区分，应让详情接口返回已有的 `displayLevel` 等明确字段。

底部按钮放在可滚动内容之外，预留原生安全区；正文和折叠说明不能被按钮遮住。无需在详情页额外添加主导航栏。

## 空状态必须按真实原因区分

| 场景 | 建议反馈 |
| --- | --- |
| 校史为空且照片也为空 | “暂无校史与老照片”“这里的故事，等待慢慢补全。” |
| 有校史但无照片 | 正常显示校史，只在照片区域说明暂无老照片 |
| 有照片但无校史 | 展示照片及年代、来源，不显示整个分区为空 |
| 近期活动为空 | “近期暂无活动”，保留查看全部，历史活动仍可通过活动列表查看 |
| 当前范围确实没有任何公开帖子 | 显示参考图“这里还没有人留下回忆”，并保留发布入口 |
| 有历史帖子，但近7天热门为空 | “近7天暂无热门内容”，提供切到最新的入口 |
| 图文筛选后为空 | 说明暂无符合筛选条件的内容，并提供清除筛选 |
| 请求失败 | 显示失败与重试，不显示“还没有人留下回忆” |
| 地点停用 | 已有资料/历史内容仍可读，底部说明不可再关联新帖子，禁用或替换发布按钮 |
| 地点不存在或缺少id | 显示明确错误和返回地图，不渲染假地点名称 |

当用户未登录时，发布流程沿用现有登录处理与编辑内容保留逻辑，不在本页提前伪装成发布成功。

## 需要处理的数据问题

### 1. 父地标与普通地点详情分流（按用户最新确认）

只读接口已核实：线上 `/api/map/places` 中，北京交通大学的 id 为 `aaaaaaaa-1111-4111-8111-000000000011`，`displayLevel=school`、`minDisplayZoom=4`，南门、思源碑、明湖、图书馆、逸夫教学楼、天佑会堂、学生活动中心、学苑餐厅、第二食堂九个节点的 `parentPlaceId` 指向它。本地也已有对应父子配置。

这是一条地点实体记录，不代表产品必须为其提供普通地点详情页面。当前普通地图组件仍读 `/api/places` 并把各地点平铺渲染，没有使用父子关系和显示层级；当前标记点击也没有区分父/子节点，统一进入 `poidetail`，因此会出现学校被当成普通地标的现象。

正确的实施范围：

- 普通地点详情面向明湖、图书馆等具体地标，不为复刻本图新增北京交通大学普通详情。
- 地图缩小到阈值以下时，在该学校树内只展示学校父地标；放大到阈值以上时展开具体子地标。阈值需按实际校园画面验证，不能把 `minDisplayZoom=4` 当成父子互斥切换已经实现。
- 建议点击学校父地标时放大并展开子地标；此点击动作是实施建议，用户目前明确的是缩放展示规则。
- 普通详情跳转、地点搜索的选择动作、发布地点候选应区分父节点和具体可发布地点，依据明确层级字段或接口用途过滤，不能按名称排除。
- 数据库保留学校父节点及其关系，不删除记录，不为了层级展示迁移已有帖子的地点归属。
- 父节点可在地图聚合子地点内容，但普通子地点详情继续只查询自身。旧的学校节点关联内容如何展示另行处理，不在本次视觉改版中删除或重绑。

如后续新增独立“学校总览”产品页，再单独设计其聚合范围与入口；当前不将其作为本页复刻前提。

### 2. “从未有内容”与筛选空结果

当前详情接口的 `postCount` 实际是 `posts.rows.length`，受排序窗口与返回数量上限影响，不是独立的全量帖子总数。

尤其默认热门时，近7天没有帖子会直接返回 `posts: []`。当前前端又优先按 `place.posts.length === 0` 显示“这个地点还没有内容”，使后面的“超出热门窗口”分支无法正确描述这种情况。

建议详情至少返回明确的数据：

- 当前范围全部公开帖子总数。
- 当前排序/内容筛选的匹配数量。
- 实际返回的预览条目及是否还有更多。

字段命名在实施时确定；不要把有限预览数量当作总量。只有全量数确实为0时，才能使用“第一位记录者”的邀请文案。

### 3. 内容筛选与预览上限

现有“仅看图文”在前端过滤已取回的有限帖子。前面若都是纯文字，即便后面还有图片帖，也可能得到误导性的空结果。

推荐将内容类型过滤交给服务端，在限制条目数量之前执行；并明确图文与纯文字的分类标准。父地点聚合时，同样需要在完整范围内先筛选、再排序、最后取少量预览。

### 4. 默认排序与参考图差异

参考图选中“最新”，当前代码依据既有 PLACE-002 约定默认“近期热门”。本方案不因一张截图直接覆盖业务默认：先保留热门默认，复刻两个标签及选中样式；如要求首次进入也完全一致，实施时需明确把默认值与相应规范一起改为最新。

无论默认哪个，热门规则继续由服务端执行：近7天发布，点赞×2＋有效评论×3＋收藏×1，减去发布超过24小时后的衰减。说明区展示此口径，不由前端重排有限预览。

### 5. 加载与错误范围

详情目前是一次组合请求，切换排序会把整个页面换成加载页。建议首次加载显示骨架；切换排序时保留已加载的基础资料，只在帖子区显示忙状态，并用请求序号/取消机制防止旧结果覆盖新选项。

组合接口任意子查询失败时，当前通常会整页失败。首轮保留整页明确重试也可以；若需要真正的“活动失败但基础资料可用”等部分成功状态，必须补充分区状态或拆分接口，不能把失败子查询替换为空数组。

## 实施顺序与工作量

以熟悉本项目的一名开发者估算：

1. 普通地点的视觉复刻、装饰、固定发布栏、折叠说明：约1–2人日。
2. 空态判定、真实数量、服务端内容筛选、局部加载及回归：整体约2–3人日。
3. 父地标缩放显隐、元数据接入、点击分流与地图回归另估约1–3人日，不与普通地点详情混作同一页面。

本轮详情复刻按具体子地标验收。图中所有资料为空只是一个状态，实施时必须同时保留有校史、有照片、有活动和有帖子的正常界面。

## 验收与运行环境

- 至少检查320px、390px及桌面居中布局，长名称和地址不与装饰相撞，底部发布栏不遮挡正文。
- 无校史/无照片、单独有资料、活动为空、有图文/纯文字、历史帖超出热门窗口、筛选后为空分别验证。
- 校史照片显示真实年代与来源；图片失败不导致整个分区塌陷。
- 普通地点、停用地点、非法id、请求失败都有可验证结果；地图中的学校父节点与具体地点跳转分流，不把父节点误开成普通详情。
- 子地点详情与对应地图标记、查看全部的内容范围一致；返回地图保留视角，地图查看定位准确，发布预选具体子地标。
- 验证切换排序时的过期响应、键盘焦点、折叠区可操作性、减少动效和安全区。
- 当前本地前端已按用户要求连接线上后端，调试读取的是线上内容。本地后端的新聚合/筛选逻辑不会自动在线上生效；开发与验证这些能力应使用隔离的本机后端，部署需配套更新，不能在UI中假定线上接口已经升级。

本轮仅新增方案文档并更新入口，没有更改地点页面或发起任何线上写操作。
