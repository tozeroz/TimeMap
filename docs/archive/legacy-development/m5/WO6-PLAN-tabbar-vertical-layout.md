# FINDING + WO 计划：底部 tab 项的**排布方向**与原版不一致（竖排 vs 横排）

> 时间：2026-09-22 01:23｜来源：(A) 类呈现比对（AUDIT §7.4 第 1 项：地图/距离呈现 + 附一更正后新增的呈现比对清单）
> 方法：只读（dump bounds + 截图视觉 + 我方 DOM 实测），**未触碰原版 app、无写操作**

## 一、结论

```
ORIGINAL_TABBAR_ITEM_LAYOUT:  竖排（**图标在上、文字在下**）
OURS_TABBAR_ITEM_LAYOUT:      横排（**图标在左、文字在右**）
→ **真实偏差（DEVIATION）**，证据强度：**两条独立原版证据 + 我方直接测量**
```

## 二、原版证据（两条独立来源）

### 2.1 结构化证据：dump 的 bounds（`docs/test/original-baseline/raw-dumps/board-observation-1.xml`）

底部区（y∈[1721,1892]）内，**激活态那个 tab 项**的子节点：

```
android.widget.ImageView   (图标)  x=[136,185] y=[1746,1795]  49×49
TextView text='自定义名称6' (文字)  x=[100,249] y=[1829,1868]  149×39
```

- 图标纵向 `[1746,1795]`，文字纵向 `[1829,1868]` → **两段 y 区间完全不重叠**，图标整体在文字**上方**
- 图标水平中心 160.5，文字水平中心 174.5 → **水平方向接近同一中心线**（差 14px，属居中误差量级）
- → 这是**竖排（column）**的几何特征；若是横排，两者 y 区间应高度重叠、x 区间分离

### 2.2 视觉证据：截图 `docs/test/original-baseline/screens/trident-campus/normal.png`

视觉读图（只问底部栏）逐字回答：

> "底部导航栏里带文字的可点项有 **3 个**；每个都是**图标在上、文字在下**排列。
>  最右侧还有一个黑色圆形'+'按钮……里面是**白色'+'图案**。"

两份证据独立且一致。

## 三、我方证据（直接测量）

用 `tools/tmp/measure-tabbar.mjs`（CDP + `getBoundingClientRect`）实测，设备 dpr=1.75、viewport 618×1074：

```
text='Lemy'  item {x:61,y:1027,w:76,h:38}  icon {x:71,y:1035,w:22,h:22}  label {x:98,y:1039,w:29,h:14}
text='校园'  item {x:244,y:1027,w:71,h:38} icon {x:254,y:1035,w:22,h:22} label {x:281,y:1037,w:24,h:18}
text='地图'  item {x:422,y:1027,w:71,h:38} icon {x:432,y:1035,w:22,h:22} label {x:459,y:1039,w:24,h:14}
```

- 图标 y=1035，文字 y=1037/1039 → **y 高度重叠**，x 区间分离（71..93 vs 98..127）
- → **横排（row）**，与 `tabbar.css` 的 `.tabbar__item { display:flex; align-items:center; gap:5px }`（默认 row）一致

## 四、顺带查明 / 纠正的两点

1. **底部栏高度：原先怀疑不一致，实测基本一致。**
   我方 bar = 58 CSS px = **102 设备 px**；原版截图视觉估算"白条约占屏高 1/19~1/20" ≈ 98–101 设备 px。
   → **不是偏差**。（此前我一度据"dump 里节点高 171px"怀疑差 1.7 倍 —— 那是**可点区**含 padding，
     与"可见条高"不是同一个量，**不能直接比**。）

2. **发布 FAB：尺寸偏差**未成立/未测准 —— 见 §五。

**为什么两次像素测量都无效（留作教训）**：

```
① "逐行颜色占比"扫描 → 得出"白条高 199px、黑色区域宽 908px"
   无效原因: 底部区是**照片卡片 + 栏**的混合内容，
             "整行颜色占比"这种启发式在混合内容上不成立，黑色占比被暗色照片污染。
② 改为"只在 x=[820,1080] y=[1600,1920] 找深色外接矩形" → 得 208×199 设备 px
   无效原因: 该结果**大于** dump 里 FAB 节点外接框(171×171)，
             说明窗口内其它暗色内容被算进来了 —— 脚本自身的自查判据正确拦住了它。
→ 结论: **FAB 的"可见直径"在我现有方法下测不准**，
   因此**不得**据"原版 168 vs 我方 77"之类的数字断言尺寸偏差。
```

**FAB 的当前状态（如实记录）**：
```
ORIGINAL_FAB_TOUCH_NODE:   171×171 设备 px（x=[881,1052] y=[1721,1892]，结构化 dump，VALID）
                           —— 但这是**可点节点**，不等于可见圆直径
OUR_FAB:                   44×44 CSS px = 77×77 设备 px（DOM，VALID）
                           —— 我方 FAB 无额外 padding，故 77 ≈ 可见直径
VISIBLE_FAB_DIAMETER_BOTH: **NOT_MEASURED_RELIABLY**（两种像素方法均判 INVALID）
→ 处置: 记为**候选偏差**，需要新的有效测量方法（见 §七）
```

# WO#6 计划（提交审核；**按流程先报计划再动产品代码**）

## 一、要修什么

**底部 tab 项由"横排"改为"竖排"（图标在上、文字在下）**，与原版一致。

## 二、范围与不做的事

```
做:
  · .tabbar__item 改为 column 方向（图标在上、文字在下），并保持水平居中
  · 按原版几何定尺寸：图标 49 设备 px（≈28 CSS px）、文字 39 设备 px 高（≈22 CSS px）
    ⚠ 这两个数来自 dump 的**激活态**节点；是否与未激活态一致**未确证**（见 §四 风险）
  · 保持既有：3 个文字 tab + 右侧圆形发布 FAB、tab 高度 58 CSS px（已证一致）
不做（本单**不含**）:
  · ❌ 不改 FAB 尺寸 —— 可见直径未测准，**不凭猜测改**（§五）
  · ❌ 不改 tab 高度 —— 已证基本一致
  · ❌ 不改 FAB 颜色/图标 —— 已证一致（黑色圆 + 白色加号 ↔ 我方 rgb(17,17,17) + IconPlus）
```

## 三、Gate（须可失败）

```
① 设备实测：对每个 .tabbar__item 取 icon/label 的 rect，断言
     icon.bottom <= label.top + 1  且 |iconCenterX - labelCenterX| <= 12
   —— 即**竖排**；改之前该断言必须 FAIL，改之后 PASS
   （这与 B2 的教训一致：**先证明断言能失败**）
② 反向断言（防"改成竖排但把原有性质改坏"）：
     · 三个 tab 的文字仍是 <当前账号昵称> / 校园 / 地图
     · FAB 仍存在、仍是 44px 圆、颜色不变
     · tab 高度仍 = 58 CSS px
③ 服务端无改动 → 但仍跑一次 M5 gate 确认无回归
```

## 四、风险与未确证项（写清，不在实现里偷偷假设）

```
⚠ 1. 图标/文字尺寸取自**激活态**节点（dump 里只有激活态那个 tab 展开了子节点）。
     未激活态是否有同样尺寸**未确证** → 实现时**不按激活态硬编码**，
     而是让所有 tab 用同一套样式（这是唯一有证据支持的做法：原版只给了激活态样本）。
⚠ 2. 原版是否有"选中态"的额外视觉（如颜色/加粗）—— dump 只有一份静态快照，
     选中态与未选中态的差异**未确证**。我方现有 is-active 样式**保持不动**（不凭猜改）。
⚠ 3. 该页截图与 dump 是**同一份快照**，若原版有 A/B 或动态布局，本结论可能不普适。
```

## 五、若审核同意，实施顺序

```
1. 写 Gate ① 的判定脚本（先跑：预期 FAIL —— 证明断言有判别力）
2. 改 .tabbar__item 为竖排 + 尺寸对齐
3. 重建 APK（web build → cap sync → gradle，注意 build-android.ps1 不建 web）
4. 真机跑 Gate ①② → 预期 PASS
5. 截图与 `trident-campus/normal.png` 做视觉比对（补充证据，非唯一依据）
6. 跑 M5 server gate 确认无回归
7. 提交审核
```

## 六、为什么这值得做（对照审核的 (B) 筛条件）

```
① original evidence strong / reproducible → dump bounds（结构化、已入库）+ 截图视觉（独立）
② current absence definitely observable   → 我方 DOM 实测：确为横排
③ implementation semantics sufficiently known → 纯 CSS 改动，语义明确（图标在上、文字在下）
＋ 用户高频可达（底部导航每个页面都可见）＋ 用户可见影响大（形态差异明显）
＋ 不依赖第三方写操作 ＋ 实现依赖少（无新依赖、无服务端改动）
→ 符合审核给的优先级条件。**这也正是 (B) 格清空后仍符合三条件的等价工作。**
```
