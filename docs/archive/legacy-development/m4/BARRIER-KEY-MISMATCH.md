M4 barrier：**捕获一个会让屏障在生产中失效的真实缺陷 —— 两侧锁键不一致**

【根因】
mutationBarrier.ts 里的权威值是 0x4D344241 = **1295270465**，
但我在三个脚本里手算成了 **1295258177**（差 1 个数值）。
后果：备份侧持的锁与业务侧申请的锁**不是同一把** → **屏障在真实运行时完全不生效**。
（这同时解释了上一轮 E2 为何是退出码 0 而不是 3。）

【最值得记的一点：机制层测试为什么会"通过"】
verify-backup-barrier.sh 的 B1/B2（窗口内阻塞 2062ms 后超时、窗口后立即成功）**PASS**，
因为 holder 与被测方**用的是同一个错键**，它们互相阻塞 —— 机制是对的，
但**它证明不了"应用两侧用同一把锁"**。
这正是"测试通过但证明了错的东西"，也是最危险的一类：
如果只跑机制层测试，我会带着一个**生产不生效的屏障**去关 M4。

修法与证据：
- 三个脚本的 KEY 全部改为 1295270465，**逐条校验**（不再无条件打印成功）
- 新增 **E0 断言：两侧锁键必须一致**，且从**源码/产物**取值、不靠人记
- 重跑后：**E2 PASS**（cleanup 窗口内退出码 3 + 文件数未变，fail-closed）
  → 反证了"键不一致"确实是根因

【同时暴露的另外两个测试侧问题（未解决）】
1. E0 的取值路径写成了 /srv/campus/server/src/mutationBarrier.ts，**服务器上只有 dist/**，
   于是 sed 取空 → 断言报"键不一致"（假失败）。改为从 dist/index.mjs 里 grep
   1295270465，或把仓库里的源文件读出来比。
2. E1/E3 仍是 400：**multipart 请求格式不对**。这两条与屏障无关
   （400 发生在取锁之前），但必须先建立"无窗口时能拿 201"的**基线**，
   否则无法区分失败来自屏障还是请求本身 —— 这是上一轮就已经订下的顺序，本轮仍未做到。

【一次操作失误（工具层面，值得单独记）】
我用 PowerShell 修正 KEY 时，把结果赋给了 `$true`（PowerShell 内建常量）→ 赋值失败，
于是 `.Replace('1295258177', "$true")` 用字符串 "True" 去替换，
**把三个脚本的 KEY 改成了 `KEY=True`**（脚本被改坏），
而我当时的脚本却**无条件打印了"已修正"** —— 典型的**假确认**，
比"没改"更糟。第二次改为先做替换、再**逐行读回校验**才真正改对。
教训：**改动之后必须把结果读回来核对，而不是相信"我执行过了"**。
