E1 与 E3 **窗口内外都是同一个 400** → 说明**我的上传请求本身不合法**，
而不是"屏障把请求挡成了 400"。400 是参数校验失败，发生在**取锁之前**，
所以这两条断言**根本没有触及屏障**，它们的 FAIL **不构成对屏障的反证**。
→ 需要先修正 multipart 请求的字段（对照 POST /api/media 的实际校验：可能是

E2 的退出码 0 需要区分两种情况（本轮**无法区分，不下结论**）：
  (a) 那一刻排他窗口其实**没有生效** → cleanup 顺利取到共享锁 → 正常退出 0
  (b) 部署到服务器的 cleanup.mjs **不含屏障**（我 17:08 用 -SkipBuild 部署，

这两种的含义完全不同，必须先用**产物检查**（dist/cleanup.mjs 里有没有
pg_advisory_xact_lock_shared）把它分开 —— 这正是本项目反复强调的
"改了代码但验的是旧产物"。

还有一条我自己的检查可能是错的：
  `select count(*) from pg_locks where locktype='advisory' and objid=$KEY`
  PostgreSQL 的 advisory 锁在 pg_locks 里**拆成 classid/objid 两个 32 位字段**
  （64 位 key 的高/低 32 位），我只比较了 objid —— 所以那句
  "排他窗口已生效"**可能是一个假确认**（false confirmation）。
  应改为比较 `(classid, objid)` 对，或直接用 `pg_advisory_lock` 的持有进程 +
  `pg_locks` 全字段打印来确认。
