## 一、我做的改动与结果

按上一轮的判断（"详情页加了图片区把评论列表下推 → 目标落到视口外 → 点击落空"），
我给 `scripts/m3/device-slice1.mjs` 的 `centerOf()` 加了：

1. `el.scrollIntoView({ block: 'center' })` + 等两帧再取坐标
2. **校验中心点确实落在视口内**，不在就返回 null（让调用方报"点不到"，而不是静默点空）

改动本身是好的健壮性改进（并且 parse 通过），**但没有解决问题**：

```
=== 重跑 composer（加了滚动进视口）===
  FAIL 回复弹层没有「回复 @昵称」标题（实际: anmoss 9月1日 · 北京交通大学 而我不再觉得… 回复 2 2）
  FAIL 回复输入框占位是 'null'
  SLICE1_COMPOSER_RESULT FAIL
```

## 二、结论：**滚动不是根因**（我的假设错了）

证据：
- 用例**没有**报"找不到「回复」按钮" → `.cmt__reply` 元素找得到
- 加了滚动与视口内校验之后仍然点不开弹层
- 所以"目标在视口外"这个解释**不成立**

我把它记为一次**错误假设**：在只有间接证据时就给出了高置信判断，
并据此改了代码。改动保留（它是正确的健壮性改进），但不能声称它修了问题。

## 三、下一步：取事实，不再猜

需要一次**直接观测**（而不是再提假设）：
1. 点下去那一刻 `.cmt__reply` 的实际中心坐标是多少、视口尺寸是多少（确认落点合理）
2. 点击后**弹层元素是否存在**（`.feed__replySheet` / `.feed__replyInput` 等）；
   若存在但内容不对，是渲染问题；若不存在，是点击没生效或被拦截
3. 页面上是否有**遮罩/其它元素**盖住了该点（用 `document.elementFromPoint(x, y)` 看实际命中的是哪个元素）
   —— 这一条最可能直接给出答案：如果 `elementFromPoint` 命中的不是回复按钮，
   就说明有东西压在上面（此前 composer/authgate 两个用例就互相污染过）
4. 设备当前的**登录态**：回复是否需要会话？若未登录而按钮仍可点，可能跳转登录页而非开弹层
   （页面文字里没看到登录页字样，但登录态本身还没确认）

## 四、纪律记录

这一轮的价值不在"修好了什么"，而在**证伪了一个假设并停止继续猜**。
如果继续沿着"滚动"方向改（比如换成坐标偏移、加大等待），
会把一个未定根因的问题伪装成"已修"，然后在 Final Gate 里再次失败 ——
那比现在停下来取事实更糟。
