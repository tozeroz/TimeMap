## 为什么被驳回（保留原文要点，避免以后重提同一方案）

> "原版运行时使用 ImageView" **并不等价于** "Web 复刻版必须把 DOM 改成 `<img>`"。
> 如果没有正确的六个"**视觉资产 ↔ 文本 token**"映射，
> A/B/C 三种方案都会为了满足"结构像图片"这个**内部指标**而**制造新的产品偏差**。
>
> 对于 Web 实现，真正要复刻的是**用户看到的图案、几何、点击后插入的 token、
> 以及 token↔图案映射**，而**不是 Android 的 View 类型**。
> **把"DOM 必须是图片元素"写成 conformance Gate，是把原版实现细节误当成跨平台产品 contract。**

## ⚠️ 审核指出的、本计划漏掉的更严重风险

> 六格的确切 token↔drawable 映射仍不知道。例如第二格若真实是 🤩，而我们仍让它插入 👑，
> **即使换成 `<img>`，反而会制造"看起来一个东西、发送另一个东西"的更严重语义错误。**

```
现状:          渲染的图案 = 插入的 token = 同一个 emoji 字符 → 视觉与语义**自洽**
按本计划改后:  图案来自原版素材、token 仍是 mock 里的字符 → **可能不一致**
              → 这是"发错东西"，比"风格不同"**严重得多**
```

## 本计划的哪一条是错的（自我更正，写清以免重犯）

本计划 §五「验收标准」的 **① 「6 项在 DOM/控件树中呈现为图片元素（而非文本节点）」**
正是被驳回的那一条：它把**我们的实现选择**（用 `<img>`）
当成了**与原版的一致性要求**。这是典型的 **implementation-to-the-test**。

→ **正确的一致性要求应落在用户可观察的 contract 上**：
   图案、几何、点击插入的 token、token↔图案映射。
   （几何那一条 —— ②21/70/112/651 —— 是**正确**的，因为它是用户可见的；①不是。）

## 重新打开的条件（低成本决定性证据出现时）

```
· 从 adapter / ViewHolder 追到 resource-index binding
· 从数据表 / 布局 XML / 静态引用链拿到 六项 drawable ↔ token 的映射
· runtime 只读获取 ImageView 当前 drawable / resource id
```
拿到 token↔drawable 映射后，才可能既复刻外观、又保证"看到的 = 发出去的"。
