## 一、问题（已确证）

```
原版:  留言板表情行 = rvEmojiList(RecyclerView) → fl_emoji_root(LinearLayout,clickable) ×6
                                    → emotion_image(**android.widget.ImageView**) ×6
       + 154 个随包 webp 资源（array/xhs_theme_xhs_emoji_res_v2）
我方:  6 个**文字 emoji 字形**（'😂' 等字符直接渲染）
→ 抽象层次不同：原版是"图片元素"，我方是"文本字形"
```

## 二、本单**做什么**（范围严格限定）

| # | 内容 | 说明 |
|---|---|---|
| 1 | 6 个表情由**文字字形**改为**图片元素**（`<img>` 或等价） | 结构层修复 |
| 2 | **保持已设备验证的横向几何不变** | 首项左 21 / 宽 70 / pitch 112 / 末项右 651（设备 px）——这是**已 PASS 的既有验证**，不得回归 |
| 3 | **点击/选择行为保持不变** | 点一项把该表情插入输入框（既有行为） |
| 4 | **协议层仍使用文本 emoji token** | 不改数据模型、不改 API、不改 DB |
| 5 | 资产来源：**用我方自有的占位图形**（不是原版 webp） | 见 §三 |

## 三、本单**不做什么**（写清边界，防范围蔓延）

✗ 不改协议（消息体仍是 body 文本，仍可含 emoji token）

## 四、⚠️ 本单最需要审核确认的一点：**用什么图**

这是本计划的**唯一开放式决策**，我不替自己决定。三个选项：

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（我倾向）** | 用 **6 个纯色/几何占位 SVG**（明确标注"占位"） | 只验证"结构层 = 图片"这一件事；不冒充原版素材；不引入版权疑虑 | 视觉上与原版不同（但本单目标是**结构**，不是像素） |
| B | 用我们**之前从截图裁的 6 个图标**（`raw-dumps/emoji-items/`） | 视觉上更接近原版 | 它是低分辨率截图裁切（70×70、含白底），**冒充原版素材**的嫌疑；且"该画哪套图"仍无依据 |
| C | 用**系统 emoji 字体渲染成 PNG** 再当图片用 | 视觉上接近"真 emoji" | 这恰恰是被确证**不符合原版**的做法（原版不是字体渲染），且多一层运行时生成 |

**倾向 A 的理由**：本单要证明的是"**结构从 text-glyph 改为 image element**"，
用占位图形就能完整验证这一命题，且不会把"C4_EXACT_6_ASSETS 未捕获"这个未决项偷偷当成已决。
若你倾向 B 或 C，请说明——**我会按你的裁定执行，并在文档里写明这是裁定而非我的偏好**。

## 五、验收标准（先写死，避免事后凑标准）

```
EMOJI_RENDERING_STRUCTURE: PASS
  ① 6 个表情项在真机控件树/DOM 中呈现为**图片元素**（而非文本节点）
  ② 横向几何与改动前**逐项一致**：首项左 21 / 宽 70 / pitch 112 / 末项右 651（设备 px）
     —— 复用既有断言，不新造阈值
  ③ 点击某项后，输入框内**出现该表情的 token**（行为不变）
  ④ 留言板其余部分无回归；M5_SERVER_GATE_RESULT 仍 PASS
  ⑤ 协议层未变：DB 里消息体仍是文本

EXACT_ASSET_CONFORMANCE: NOT_EVALUATED   ← 明确保留为未评估，不得写成 PASS
```

**验证方法（按"oracle 来自权威观测面"纪律）**：
- ① 用 **DOM/控件树**（几何与元素类型）
- ② 用 **getBoundingClientRect 实测**（既有 `device-chat-sender-align.mjs` 的同款做法）
- ③ 用 **input.value**（而不是读界面文字）
- ⑤ 用 **DB 查询**
