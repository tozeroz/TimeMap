## 一、M5 的目标定义（先摆清楚，避免范围漂移）

M4 结束时已知有四类"没做到"的项。它们**性质完全不同**，不能用同一种方式推进：

| 类别 | 能推进吗 | 推进方式 |
|---|---|---|
| A. 未实现但**没有政策障碍** | ✅ 可以 | 正常实现 + Gate |
| B. **证据不可采信** | ⚠️ 只能实现、不能声称一致 | 实现 + `NOT_EVALUATED` 标注 |
| C. **策略阻断** | ❌ 不能取证 | 保持 `BLOCKED_BY_POLICY`，永不推进 |
| D. 已知偏差 | ⚠️ 可缩小但未必消除 | 缩小并更新偏差说明 |

M5 只做 A 和 D；B 的实现要带标注；**C 一律不碰**（这是用户硬约束）。

## 二、候选工作项（按"可验证性 ÷ 成本"排序）

### 候选 1：留言板（`board_notes`）——**推荐先做**

- 现状：模型已判定 `SUPPORTED`（用户对用户私密留言，只读证据），表结构已有，
  **但既没有接口也没有界面**
- 为什么适合先做：
  1. 原版有独立页面（`message-board`），属于 1:1 的必要部分
  2. 证据**可采信**（只读取得：`leaveMsgTip`「仅双方可见」、`tvNoComment`「可以给同学留言噢」、
     `tvSendComment`「留言」、表情行恰好 7 个）→ 可以做**真实的一致性判定**
  3. 范围小：两个接口 + 一个页面
- 计划：
  - `GET /api/board-notes/:userId` —— 我与某位同学的留言（仅双方可见：`from_user_id/to_user_id` 双向）
  - `POST /api/board-notes/:userId` —— 留言（校验：不能给自己留言、对方必须是真实用户）
  - 页面：标题「留言」+ 副标题「仅双方可见」+ 便签列表 + 底部表情行（7 个）+ 输入框
    （占位「留言仅双方可见」）+ 按钮「留言」
- Gate 断言：双方可见、第三方不可见、不能给自己留言、空态文案、
  **不声称**"便签的具体视觉样式与原版一致"（原版便签配色/字体我们只有截图，可作弱参照）

### 候选 2：语音消息（`kind='voice'`）——**次选**

- 现状：`messages.kind` 允许 `voice`，但**没有录制、没有上传、没有播放**
- 难点：需要麦克风权限与录音能力（Capacitor 插件），且原版的语音交互
  （按住说话最长 60 秒）没有只读证据 → **属 B 类**：能实现，不能声称一致
- 计划：采集 → 上传（复用 media 的 private 通道 + 新的 audio mime 白名单）→ 播放
- 注意：`media_mime_allowed` 目前只允许三种图片类型，**需要一次迁移**放宽到音频
  （并保持"按内容嗅探"的纪律：音频也要校验容器头，不能只信 Content-Type）

### 候选 3：图片压缩/重编码——**建议明确不做，并写清理由**

- 现状：上传只做结构校验与体积上限（≤5MB），不做缩放/重编码
- 不做的理由：服务器 396MB 内存 + 单文件打包 + 无 `node_modules`，
  引入 native 图像库（sharp）会破坏部署模型；纯 JS 方案（jimp）体积/内存不划算
- **建议**：把它记为**明确的设计取舍**（不是遗漏），并在文档里写清：
  "大图按原样存储、由客户端负责缩放" —— 因为原版客户端本来就做压缩，
  服务端不做并不影响 1:1 的用户可见行为
- 若要推进，唯一合理路径是**客户端侧压缩**（Capacitor 下可用 canvas 缩放），
  这属于客户端工作，可单独成一单

### 候选 4：`@所有人` —— **建议保持不做**

- M4 已明确不做，理由是"避免与'提到某人'在数据上无法区分"
- M5 若要支持，必须**先定义语义**（例如 `mentioned_user_id = NULL` 表示全体，
  或单独一张 `message_mention_all(message_id)`），并说明这与原版的关系
  —— 而原版语义**没有只读证据**（at-panel 证据已判 INADMISSIBLE）→ 永远只能 `NOT_EVALUATED`
- **建议**：除非审核要求，否则保持不做，并在总表里保留该行

### 候选 5：per-user 配额——**建议明确记为已知限制**

- 现状：任何账号都能占满盘（20GB）
- 权衡：真实产品需要，但 demo 规模下实现它没有验证价值
- **建议**：保留为已知限制，写进审计表（已写），不实现
