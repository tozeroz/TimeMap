## 四、决定性的检验（下一轮做，纯本地可做）

**思路**：如果原版用的是**平台彩色 emoji 字体**（Noto Color Emoji），
那么它渲染的 😂 与**同一平台上字体渲染的 😂**在**字形上应高度一致**（同字体，只是尺寸不同）；
如果原版用的是**自定义位图素材**，字形会与平台字体渲染**系统性不同**。

**可行做法**：
1. 在我们自己的 App（WebView）里把同一字符（😂）渲染并截图
2. 缩放到与原版 70×70 裁图同尺寸，做**逐像素/结构相似度对比**
3. 同时对照**已知的位图素材案例**（例如我们 demo 里若用了 PNG 图标）作为阴性对照

⚠ 该检验的**已知局限**（必须写进结论，否则又会变成过度声明）：
- WebView 与原生 ImageView 的渲染管线不同（字体 hinting、gamma），会有系统偏差
- 因此相似度**只能作旁证**，不能单独定论；若两者高度一致则强烈支持"字体渲染"

## 六、重要修正：这两份证据**强度不对等**，我下调时把它们当成了对等冲突

紧接着写下"UNRESOLVED"之后，我重读了结构级证据，发现**我低估了自己手上的东西**。

### 结构级证据其实不只"名字暗示"，还有一条正面的观测

```
观测 1: 该节点是 com.kairuotu.campus:id/emotion_image（Image 命名）
观测 2（更强）：**dump 里根本没有表情字符文本** ——
         text / content-desc 里找不到任何 emoji 字符；
         而同一次 dump 里能看到「留言」「仅双方可见」「可以给同学留言噢」等
         TextView 的可见文本（说明 uiautomator 对 TextView 文本是**正常暴露**的）。
```

**观测 2 的意义**：若原版用 `TextView` 渲染 emoji 字符，uiautomator 通常会像暴露
「留言」那样把该字符暴露在 `text` 里。它没有 → **与"文字字形"不符**。
这**不是**照名字推断，而是**从"应该出现却未出现"得到的证据**。

### 因此两份证据的强度对比是：

| 证据 | 内容 | 强度 | 性质 |
|---|---|---|---|
| **结构级** | 无 emoji 文本 + `emotion_image` 节点 | **强** | 直接观测（控件树） |
| **像素级** | 边缘平滑像字体渲染 | **弱** | 视觉模型自认在 70×70 截图上无法断定 |

**即：这是"强证据 vs 弱证据"，不是"两份对等证据冲突"。**

### 修正后的结论

```
EMOJI_NODE_KIND: 支持"图片/非字符字形"（依据强证据）
  强证据: 控件树里无 emoji 字符文本（而同树能暴露其他 TextView 文本）+ emotion_image 节点
  弱反证: 像素边缘更像字体渲染（视觉模型自认无法断定）
→ 两者**不对等**；按本项目"证据强度分级"的纪律，**强证据优先**。
→ 但为审慎，仍保留 UNRESOLVED 的**状态标记**，理由：
   强证据是"间接正面"（从缺失推断），而非"直接指名"（例如拿到 drawable 资源清单）。
   若要有直接证据，需读 APK 资源或该 view 的 drawable —— 目前无手段。
```
