# M5 留言板设备端验证状态

M5 留言板设备端：四次注入尝试结论明确——React 受控 state 无法被合成输入更新（下一步改用"点表情"）

【决定性数据（查 Nginx 访问日志）】
四次尝试，每次点击「留言」都发出 POST，且**每次都回 400 bad_body（响应体 20 字节）**：
  16:49:50  400   （原生 setter + input 事件）
  16:50:30  400   （Input.insertText）
  16:50:58  400   （insertText，复跑）
  16:52:32  400   （逐字符 keyDown/char/keyUp）
其中最后一轮**输入框的 value 与期望完全一致**，POST 仍是 400 ——
即 DOM 值对了，但 React 的受控 state 没有更新（受控输入会在下次渲染时回退 DOM 值，
我读 value 的时机恰在回退之前，所以看起来是对的）。

【结论】
- **产品无责**：服务端对"空正文"回 400 是**正确行为**（与 verify-board-notes.sh 的 B4 组一致），
  且四次都能收到请求（点击链路是通的）。
- 瓶颈在**我们的合成输入手段**：四种方式都无法让 React 19 在这个 Capacitor WebView 里
  接受合成文本。这是测试 harness 的限制，不是产品缺陷。

【下一步（有明确依据的方案，不是再试一次）】
**用"点表情"产生正文**：表情按钮的 onClick 是 **React 自己调用**的
`setDraft(prev => prev + emoji)` —— 只要用真实触摸点一下表情，
state 里就有了真实文本，**完全不依赖任何注入**。
然后再点「留言」→ 应该得到 201 与便签。
这个方案的好处：既绕开 harness 限制，又**没有为了让测试通过而改动产品代码**
（给输入框加 test-only 入口那种做法是产品为测试让路，方向反了）。

【本轮的一个操作失误（如实记）】

本轮没有把上述方案落地。这不是分析错误，是编辑方式的问题 ——
下一轮改用 write 工具整段重写该脚本片段，避免再在 shell 引号上栽跟头。
（这个项目已经在 shell 引号上栽过多次：中文引号、反引号、here-string，教训是同一条：
**复杂文本用文件工具写，不要塞进命令行**。）

【纪律记录（第五次）】
"输入框 value 正确但 POST 400" 这个组合是**关键区分信号**：
它把"UI 显示"与"组件状态"分开了，也把"产品拒绝空正文"与"产品写不进去"分开了。
只看界面会得出"输入框正常"，只看 400 会得出"接口有问题"，两者都不对。

M5 留言板设备端：点表情成功进入 React state，但提交仍为空正文（下一步直查请求体）

【决定性数据】
  16:54:22 GET  /api/board-notes/2222… 200（进入页面）
  16:54:30 POST /api/board-notes/2222… **400**，响应体 20 字节 = bad_body
  16:54:33 GET  /api/board-notes/2222… 200（提交后的重新拉取）
而界面实测：点了表情「😂」后**输入框 value = "😂"**（脚本断言 PASS）。

即：**表情按钮的 onClick（React 自己调用）确实让输入框显示了 😂，
但点「留言」时 post() 里的 draft 仍是空串。**

【这排除了什么、还剩下什么】
已排除：
- 点击链路（POST 确实发出）
- "合成输入无法进 state"（点表情能进，说明 state 通路本身是通的）
- 产品接口（空正文 → 400 是正确行为）
剩下两种可能（下一轮用一次实验区分）：
  A. `busy` 卡在 true（按钮 disabled），而 16:54:30 那次 POST 是别的原因触发的 → 需要看按钮的 disabled 状态
  B. post() 读到的 draft 与界面显示的 value 不是同一份状态 → 需要在页面里把
     "提交时的 draft 实际值" 打出来（例如临时读取 React 内部不可行，改为让 post() 把
     提交内容写进 console，再从 CDP 的 Runtime.consoleAPICalled 抓）
更简单的判定法：**在页面上直接读 .board__input.value 与 .board__send.disabled 两个值**，
并对同一次提交同时抓"请求体"（从 CDP Network 域或服务端日志的响应体）——
两者一比就知道是"发空了"还是"没发"。

【本轮进展小结（有价值的部分）】
"点表情 → React state" 这个绕开注入的思路**被验证是可行的**（value 确实变了），
所以问题已经不在 harness 的输入能力上，而在**提交那一刻读到的状态**。
这把排查范围收窄了一大步。

【纪律记录（第六次）】
我没有因为"输入框显示 😂"就认为状态没问题，而是去查了请求结果 ——
结果两者矛盾（界面有值、请求为空）。**"界面显示的值"与"代码实际用的值"可以不同**，
这一点在受控组件里尤其容易发生。若只看界面就会得出"功能正常"的错误结论。
