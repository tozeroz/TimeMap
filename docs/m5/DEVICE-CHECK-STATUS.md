# M5 留言板设备端验证状态

M5 留言板设备端：四次注入尝试结论明确——React 受控 state 无法被合成输入更新（下一步改用"点表情"）

【决定性数据（查 Nginx 访问日志）】
四次尝试，每次点击「留言」都发出 POST，且**每次都回 400 bad_body（响应体 20 字节）**：
  16:49:50  400   （原生 setter + input 事件）
  16:50:30  400   （Input.insertText）
  16:50:58  400   （insertText，复跑）
  16:52:32  400   （逐字符 keyDown/char/keyUp）
其中最后一轮**输入框的 value 与期望完全一致**，POST 仍是 400 ——
即 DOM 值对了，但 React 的受控 state 没有更新（受控输入会在下次渲染时回退 DOM 值，
我读 value 的时机恰在回退之前，所以看起来是对的）。

【结论】
- **产品无责**：服务端对"空正文"回 400 是**正确行为**（与 verify-board-notes.sh 的 B4 组一致），
  且四次都能收到请求（点击链路是通的）。
- 瓶颈在**我们的合成输入手段**：四种方式都无法让 React 19 在这个 Capacitor WebView 里
  接受合成文本。这是测试 harness 的限制，不是产品缺陷。

【下一步（有明确依据的方案，不是再试一次）】
**用"点表情"产生正文**：表情按钮的 onClick 是 **React 自己调用**的
`setDraft(prev => prev + emoji)` —— 只要用真实触摸点一下表情，
state 里就有了真实文本，**完全不依赖任何注入**。
然后再点「留言」→ 应该得到 201 与便签。
这个方案的好处：既绕开 harness 限制，又**没有为了让测试通过而改动产品代码**
（给输入框加 test-only 入口那种做法是产品为测试让路，方向反了）。

【这排除了什么、还剩下什么】

- "合成输入无法进 state"（点表情能进，说明 state 通路本身是通的）

     "提交时的 draft 实际值" 打出来（例如临时读取 React 内部不可行，改为让 post() 把
     提交内容写进 console，再从 CDP 的 Runtime.consoleAPICalled 抓）
更简单的判定法：**在页面上直接读 .board__input.value 与 .board__send.disabled 两个值**，
并对同一次提交同时抓"请求体"（从 CDP Network 域或服务端日志的响应体）——
两者一比就知道是"发空了"还是"没发"。

M5 发现并修掉一个**真实的前端 bug**：body 双重 JSON 编码（400 bad_body 的真正根因）

【决定性实验（页面内、同一个 token、同一个 URL、同一个 body）】
  不带 Content-Type:  400 {"error":"bad_body"}
  带 Content-Type:    201 {"id":"f86e9d74-…"}
→ 证明 400 不是"测试注入的问题"，而是**真实缺陷**。

【真根因：我新写的 postBoardNote 传了字符串】
client.ts 的 request() 内部本来就会 `JSON.stringify(init.body)`；
而 postBoardNote 原来写的是 `body: JSON.stringify({ body })` ——**又 stringify 了一次**。
结果请求体变成 JSON 字符串字面量（"{\"body\":\"😂\"}"），服务端解析出来是**字符串**而非对象，
`req.body.body` 为 undefined → 正确地回 400 bad_body。
修法：`body: { body }`（传对象，序列化只在 request() 里做一次）。
已检查：client.ts 里**没有其它同类双重编码**（另两处是正确用法与 localStorage）。

【症状为什么极具欺骗性（值得记）】
界面输入框显示正常 → 看起来前端没问题；
请求确实发出 → 看起来点击没问题；
服务端稳定 400 → 看起来接口有问题；
而我先后三次把它判成"测试 harness 的注入限制"。**三次都判错了。**
真正把它揪出来的是那个"只差一个请求头"的对照实验 ——
**当"改一个变量就能从失败变成功"时，就该做这个实验，而不是继续推测。**

【修复后设备端仍 400（开放问题，未下结论）】
修复并重建 APK（tsc 通过、BUILD SUCCESSFUL、cap sync 完成）后，设备端 POST 仍是 400。
因此**不能声称已修复闭环**。最可能的解释：装到设备上的仍是旧 bundle
（需要下一步核实 APK 里 JS 的内容/时间戳，或彻底卸载重装后再验）。
其它可能：还有第二处编码问题；或 WebView 缓存了旧资源。
下一步第一件事：**核实设备上运行的 bundle 是否包含本次修复**，
否则后面的验证都是在验旧代码（这正是我此前在 M4 收口时强调过的"改了代码、验的是旧产物"）。
